# Этап 1.4 — серверное прохождение тематических вариантов

Реализованы API и сервис попыток, серверное время, скрытие, атомарное удаление.
Ученические HTML-страницы, каталог с реальными результатами, отдельный result API
с эталонами и общая история пока не подключены: это этап 1.5. Автосохранение сейчас
предоставлено как серверный PUT API; debounce/очередь браузера подключаются вместе
с настоящей страницей прохождения на этапе 1.5.

## API

Все изменяющие запросы — JSON, Flask-сессия и `X-CSRFToken`. Владелец определяется
только по сессии. GET не создаёт новую попытку. API не даёт административного обхода
владения: просмотр других учеников через отдельные административные экраны будет
подключаться отдельно. Текущие административные API опубликованных media сохранены.

| Метод и URL | Тело / назначение |
| --- | --- |
| POST `/api/thematic-variants/<id>/attempts` | `request_key`; новая или существующая active |
| GET `/api/thematic-attempts/<id>` | Свои условия, ответы, ревизии, версия, серверное время; finished также доступна после скрытия/удаления |
| PUT `/api/thematic-attempts/<id>/answers/<item_id>` | `answer`, `expected_revision`, `mutation_id` |
| POST `/api/thematic-attempts/<id>/check/<item_id>` | `request_key`, `expected_revision`, необязательный `answer`; проверка сохранённого либо атомарно сохранённого нового ответа |
| POST `/api/thematic-attempts/<id>/submit` | `request_key`, необязательный `answers: [{item_id, answer, expected_revision}]` |
| GET `/thematic-attempts/<id>/media/<media_id>` | Только материал версии своей попытки; active — condition/attachment, finished — также reference |
| DELETE `/api/admin/thematic-variants/<id>` | Только администратор: `confirmed: true`, `expected_revision`, `request_key` |

Ключи операций: 16–100 ASCII букв, цифр, `_` или `-`; рекомендуется UUID.
После сетевого сбоя повторяется **тот же ключ и то же тело**. Новое действие получает
новый ключ. Ревизия ответа начинается с 0. Сохранение всегда увеличивает её на 1,
даже при одинаковом тексте; replay прежней мутации не увеличивает повторно.

`answer`: строка для scalar, две строки для pair, прямоугольная матрица строк для grid.
`null` очищает любой формат. Неправильная форма/чужой item_id отклоняются. Размер одного
ответа ограничен 100 000 символов JSON; общий запрос — 2 МБ. Проверка пустого ответа
возвращает `EMPTY_ANSWER`, при завершении пустой ответ становится skipped/0.

Успешный check возвращает `is_correct` и служебные revision/time/replayed, без эталона
или частичного балла. Повтор старого check после нового save возвращает результат
**проверенной старой revision** и `current_revision`; UI не должен переносить старую
проверку на изменённый ответ. GET актуального ответа после изменения показывает
`is_correct: null` до новой проверки. Сохранённый клиентский is_correct игнорируется.

Ошибки: 401 нет сессии, 404 чужая/несуществующая попытка или задача, 409 конфликт
ревизии/завершённая попытка, 423 VARIANT_HIDDEN, 410 VARIANT_DELETED, 429 RATE_LIMITED,
503 неподготовленная/занятая БД. 409 ответа содержит актуальную revision, но не чужие
данные. Технический лимит новых save/check — 240 за 60 секунд на пользователя; replay
успешных операций не расходует лимит. Он не ограничивает число попыток или время решения.

## Транзакции и история

Start сериализуется через BEGIN IMMEDIATE и частичный UNIQUE active. Все start-ключи,
включая ключи повторного открытия существующей active, записываются в operation_keys.
Их повтор после finish не создаёт следующую попытку. Новый ключ после finish создаёт
новые attempt_id/no. Snapshot/version_id старой active не переключается при публикации.

Save/check используют CAS по каждому ответу и operation_keys. Повтор запроса с
прежним ключом, но другим телом, даёт 409. Проверка скрытия/удаления выполняется под
write-lock до обработки replay: старый пакет не обходит новую блокировку.

Submit применяет весь финальный CAS-пакет либо ничего, затем независимо от предыдущих
check заново проверяет ВСЕ N последних сохранённых ответов по snapshot/grader_version.
Правила нормализации — существующий бинарный ordinary-binary-v1, а не правила тестов.
Итог 0/1 на задачу, без частичных баллов и шкалы ЕГЭ. Фиксируются время, причина,
S/N и final_status. Триггеры запрещают дальнейшее изменение результата/ответов.
Повтор submit уже finished возвращает прежнюю сводку, игнорируя поздний пакет — в том
числе после системного завершения при удалении.

GET attempt пока не выдаёт эталоны даже для finished; отдельное представление полного
результата относится к 1.5. Сами эталоны и media остаются в неизменяемой версии.
Все новые персональные ответы no-store. Право на media проверяется по владельцу,
версии, роли и видимости; произвольного пути/доступа к другой версии нет. Хэш копии
проверяется перед выдачей. Проверка доступа линеаризуется под блокировкой БД; уже
разрешённый параллельный запрос нельзя «отозвать» после начала ответа.

Удаление в одной транзакции: CAS/подтверждение → deleting → единый t_delete → закрытие
открытого скрытия → перепроверка и завершение всех active → удаление draft → tombstone
deleted с пустым current_version_id → ревизия каталога и receipt. Версии, items, ответы,
завершённые попытки и файлы не удаляются. Сбой на любом шаге возвращает прежние данные.
Подготовленная до удаления публикация повторно проверяет состояние и не воскрешает вариант.
Нагрузка большой массовой финализации требует измерения на целевом объёме перед production;
здесь нет фонового worker или частичных commit. SQLite lock timeout — штатный timeout
соединения (5 секунд), HTTP API отвечает 503 при занятости.

## Время

Только серверные миллисекунды после получения блокировки. Из [started_at, submitted_at)
вычитаются пересечения со всеми скрытыми интервалами variant_id, в том числе открытым
при системном удалении. Уход со страницы и обычные перерывы включаются. Hide/show/publish
учитывают последние записанные события, чтобы откат часов не создавал отрицательных
интервалов. Готовое elapsed_ms неизменно после finish, будущие hide/show его не меняют.

## Безопасная проверка

Результат этапа: **77 тестов прошли** (59 тематических, 18 прежних регрессионных
и проверок изоляции). `node --check` и `git diff --check` без ошибок. SHA-256
`users.db` и `.local-data/dev-users.db` совпадает до и после работы. Установленная
среда — Python 3.12.10 / SQLite 3.49.1; SQL не использует возможностей новее 3.26,
но отдельный запуск на движке 3.26 в этой сессии не выполнялся.

Запуск тестов из корня, без запуска Flask-сервера:

```powershell
& 'C:\Users\Артем\AppData\Local\Programs\Python\Python312\python.exe' -B -X utf8 -m unittest discover -s tests -v
node --check static/js/admin/thematic/manage.js
```

Тесты создают временные SQLite-базы с вымышленными пользователями, backup и миграцией.
Проверяются start/replay/CAS, строка/пара/матрица, финальная перепроверка, атомарность
CAS-пакета, владельцы/CSRF, закрытые media, замена публикации без смены active-версии,
многократное скрытие и часы, удаление нескольких active, откат позднего сбоя,
конкурентные start/save/finish/hide/delete и публикация, подготовленная до удаления.
Регрессионные тесты прежних разделов также выполняются на временных данных.

Для ручной проверки использовать **отдельную копию для проверки**, уже подготовленную
по `docs/THEMATIC_STAGE_1_3.md`; никаких миграций на users.db/dev-users.db. Обновление
1.4 не требует новой миграции. Запуск/перезапуск собственного проверочного экземпляра
владелец выполняет самостоятельно с EGEVOLUTION_LOCAL_CHECK=1 и явным EGEVOLUTION_DB_PATH.
Агент работающий сервер не запускает и не останавливает.

В административном каталоге появился DELETE с предупреждением о завершении active
и сохранении истории. Проверять его только на варианте в отдельной тестовой копии.
Для API в той же локальной браузерной сессии можно использовать DevTools, извлекая
CSRF из `meta[name="csrf-token"]` страницы управления. Пример помощника:

```javascript
const csrf = document.querySelector('meta[name="csrf-token"]').content;
async function thematicRequest(url, method = 'GET', data) {
  const r = await fetch(url, {
    method, credentials: 'same-origin',
    headers: {'Content-Type': 'application/json', 'X-CSRFToken': csrf},
    body: data === undefined ? undefined : JSON.stringify(data)
  });
  return {status: r.status, data: await r.json()};
}
// Подставить ID опубликованного варианта именно в отдельной тестовой копии.
// POST /api/thematic-variants/ID/attempts, {request_key: crypto.randomUUID()}
// GET /api/thematic-attempts/ATTEMPT_ID → взять item_id/revision
// PUT .../answers/ITEM_ID, {answer: '...', expected_revision: 0, mutation_id: crypto.randomUUID()}
// POST .../check/ITEM_ID, {expected_revision: 1, request_key: crypto.randomUUID()}
// POST .../submit, {request_key: crypto.randomUUID()}
```

Административная тестовая сессия создаёт попытку своего пользователя. Проверки отказа
другому пользователю/прав администратора уже покрыты автоматическими тестами.
Реальные ученические страницы и общая история не подключаются до согласования этапа 1.5.
