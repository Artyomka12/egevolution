# Поэтапный план обновления ЕГЭволюции

Дата: 13.10.2026. Статус: план для утверждения. Реализация не начата.
Связанный документ: [TESTS_TECHNICAL_SPEC.md](TESTS_TECHNICAL_SPEC.md).

## 1. Правила выполнения

Работать последовательно, по одному отдельно подтверждённому этапу. Завершение этапа означает: код рассмотрен, проверки пройдены, описан откат, есть демонстрация результата; это не автоматическое разрешение на следующий этап или production-публикацию.

В рамках текущей задачи актуализируются только эти два документа. Не изменяются `app.py`, SQLite, JSON-контент, зависимости, семь прототипов тестов и утверждённый prototypes/thematic/editor.html. Приложение не импортировалось, миграции и серверные тесты с его запуском не выполнялись. Прототипы прочитаны как эталоны интерфейса; их JS не принимается за реализацию безопасности и хранения.

Обозначения: «существующие» — реально обнаруженные файлы; «новые» — проектные имена будущих файлов. Их создание разрешается только после согласования этапа. В таблицах путей группы в фигурных скобках означают отдельные файлы. Если новый контекст потребует других путей, сначала обновить перечень этапа, не расширять работу незаметно.

## 2. Что меняется и что сохраняется

### 2.1 Тесты

Новый модуль Flask Blueprint с отдельными таблицами SQLite для тестов, черновиков, неизменяемых версий, попыток, ответов, оценок, grants и идемпотентности. Серверные дедлайны, один пишущий клиент, автосохранение с ревизиями, фоновые timeout, оценки 0/1. Ученическая часть на текущей светлой системе; административная — на текущей тёмной. Семь утверждённых прототипов не изменяются.

Ученик получает подробности только последней попытки, администратор — всей истории. Лучший результат теста определяется максимальным процентом по всем полностью проверенным версиям. Все эталоны скрыты до полной проверки попытки. Подтверждённое удаление любого теста, включая active, уничтожает его попытки и результаты атомарно. Правила скрытия тематических вариантов на тесты не переносятся.

Результаты тестов не попадают в legacy `user_results` и не меняют шкалу ЕГЭ. Отдельной статистики тестов в личном кабинете ученика нет. Просмотр результата из каталога остаётся.

### 2.2 Варианты

Существующие `variants/variant_01/variant_01.json` … `variants/variant_20/variant_20.json` сохраняются без пересборки. `/variants` получает переключатель «Полноценные варианты / Тематические варианты», по умолчанию полноценные. Текущий `templates/variant_list.html` пока содержит единую сетку без переключателя: требуется добавить поведение, а не предполагать наличие готового компонента.

Тематические варианты имеют отдельное пространство ID и отдельный обычный режим. Нет экзаменационного режима, шкалы ЕГЭ и кнопки его выбора. Повторяющийся номер ЕГЭ — нормальное состояние, а не ошибка. Отдельный конструктор следует утверждённому prototypes/thematic/editor.html; существующий конструктор полноценных вариантов не меняется. SQLite хранит черновики, неизменяемые снимки публикаций и попытки; отдельный каталог тематических JSON не создаётся. Лучший результат: сначала число полностью правильных задач, затем процент. Скрытие блокирует active и исключается из времени; удаление завершает active и сохраняет историю. Подробная архитектура — раздел 6.

### 2.3 Теория

Переиспользуются `theory/task_XX/theory.json`, `theory.description`, `theory.images` с `after_paragraph`, `templates/teoria_zadanie.html`, `templates/constructor_theory.html`, `replace_markers`, `static/css/pages/teoria.css`, `static/css/design-system.css`.

Многострочный `<pre>` и изображения уже поддерживаются; полноценной подсветки Python в изученных файлах нет. Нужна безопасная подсветка с сохранением буквальных пробелов/переносов и без выполнения кода, а не новый формат всего контента.

**Обнаружена выполненная перенумерация v2.12.0.** Текущий `theory/task_10/theory.json` называется «Организация компьютерных сетей. Адресация», №13 — «Оператор присваивания и ветвления. Перебор вариантов». `CLAUDE.md`, `scripts/DEPLOYMENT.md`, `scripts/renumber_ege_tasks.py` описывают перенос 13→10 и 23→13, архив `.local-data/ege-renumber-2026.json`. Перед изменением двух схем IP всё равно требуется подтверждение преподавателя и сверка фактического production: локальное состояние не доказывает, что сервер уже мигрирован. Повторно запускать старую перенумерацию нельзя.

## 3. Карта существующих ограничений и рисков

| Область | Подтверждённое состояние | Следствие для плана |
|---|---|---|
| Инициализация | `app.py` вызывает init_db при импорте, может создать администратора и вывести его пароль | Нельзя запускать служебный импорт на рабочей БД; сначала изоляция/отдельный bootstrap |
| Доступ | Сессия, CSRFProtect, проверки is_admin уже есть; общий before_request делает redirect | Новый JSON API должен возвращать корректные 401/403 и проверять владельца каждого объекта |
| SQLite | Путь users.db зашит в get_db, FK явно не включены | Конфигурируемый путь и проверка существующих сирот до FK |
| Удаление ученика | delete_user не очищает все progress/last_answer | Без исправления включение FK сломает удаление или сохранит сироты |
| История вариантов | Связь ответа с попыткой через дату до минуты | Не использовать для тестов/тематических; не пытаться угадывать миграцию старых совпавших дат |
| Проверка ЕГЭ | get_points_for_task зависит от номера, конвертация шкалы отдельная | Тесты имеют свой grader; тематические получают отдельную политику правильности |
| Таймер вариантов | Клиент передаёт time_remaining и time_spent | Новый серверный таймер нельзя получить простым копированием |
| Эталоны | exam/reshenie сериализуют полный tasks | Тестам нужен публичный DTO без ответов; риск старого экзамена отдельно учесть |
| Конструктор вариантов | tasks — словарь по номеру ЕГЭ, минимум 27; позиция=номер | Повторы 1..10 не поддерживаются без нового формата/адаптера |
| Контент | JSON и SQLite записываются отдельно | Нужны согласованные backup и обработка незавершённой файловой записи |
| Теория | Практика индексируется позицией idx+1 | Удаление/перестановка практики меняет смысл прогресса; правки статьи отделять от практики |
| Security log | DEVELOPMENT_LOG отмечает исправления CSRF/XSS, но состояние менялось | Не объявлять всё безопасным по старому отчёту; проверить актуальные обработчики |
| Загрузка/удаление | Есть magic bytes; theory API принимает список путей от клиента | Серверный реестр принадлежности и canonical path до удаления, проверка декодирования |
| Визуализатор | tracer.py выполняет exec в процессе | Не использовать в тестах; отдельная оценка ресурсной изоляции, без утверждения доказанного обхода |

Исправления ранее закрытых CSRF, SQL-параметризации, whitelist-разметки, POST logout и safe next сохраняются. Не возвращать raw `|safe`, передачу секретов в JS и GET-мутации.

## 4. Резервное копирование, миграции и откат

### 4.1 Согласованный резервный комплект

До первой миграции и перед каждой production-публикацией создать комплект с одним manifest/release ID:

1. Серверная `users.db` через SQLite backup API. Не копировать только основной файл во время активных WAL-записей.
2. `tasks/`, `variants/`, `uroki/`, `theory/`: JSON и связанные изображения/файлы/видео; `static/uploads/`, private `data/tests/media/` и `data/thematic/media/`, когда появятся. Копировать и неизменяемые файлы старых версий, а не только текущие ссылки каталога.
3. `.local-data/ege-renumber-2026.json` вместе именно с соответствующей БД. Архив содержит привязки к ID и границам ответов; его нельзя переносить к другой БД.
4. Коммит кода, схема миграций, хэши контента, версия Python/SQLite, перечень таблиц и количества строк. Проверочные manifest не содержат секретов/полных ученических ответов.
5. Конфигурация запуска/Passenger WSGI и секреты — отдельный защищённый процесс восстановления владельца. Не выводить `.env` и не включать его в Git/публичный manifest.

Хранить вне webroot с ограниченными правами; проверить свободное место, недоступность backup по HTTP и вторую копию вне сервера. Срок хранения, шифрование, RPO/RTO согласовать. Предложение для релиза: нулевая потеря данных при восстановлении до открытия записи; время полного восстановления измерить на rehearsal, не обещать заранее.

Для согласованности БД и файлов включить техническую паузу, остановить все писатели и worker, дождаться завершения процессов. Пауза через отдельный WSGI с 503, который не импортирует app.py, соответствует существующему `scripts/DEPLOYMENT.md`. SQLite online backup без паузы не гарантирует согласованность с одновременно редактируемым JSON.

После появления тестов перед плановой паузой заранее закрыть новые старты и дождаться окончания active; их дедлайн автоматически не замораживать. Если ожидание невозможно, применяется утверждённая процедура аварийной компенсации. Регулярное резервирование после запуска тоже входит в эксплуатацию: расписание и хранение согласуются на этапе 0.1, автоматический backup и периодическая проба восстановления проверяются на этапах 1.6 и 3.6. Для согласованной копии без общей паузы потребуется отдельно спроектированный протокол фиксации версии контента; простую онлайн-копию SQLite не объявлять полной резервной копией платформы.

### 4.2 Проверка восстановления — обязательный этап

В отдельном временном каталоге восстановить комплект, не поверх рабочего проекта. Проверить SHA файлов, `PRAGMA integrity_check`, ожидаемые FK/сироты, количество строк, открытие медиа, соответствие архива истории. Запустить приложение только с временной БД, фиктивными секретами и отключёнными уведомлениями. Просмотреть старую попытку, новый тест после появления, вход/роли, урок и теорию. Записать длительность и результат. Наличие файла backup без успешного восстановления не является критерием готовности.

### 4.3 Безопасные миграции
**Проверенное локальное состояние на 13.10.2026:** users.db открыта только на чтение; таблицы schema_migrations нет, каталога migrations нет. Production в этой задаче не проверялся. До разработки миграций отдельно прочитать его журнал и сопоставить фактическую схему, имена и checksum; отсутствие журнала при наличии новых таблиц — причина остановиться и согласовать baseline, а не применить CREATE вслепую.

Для чистой базы план: migrations/001_thematic.sql на этапе 1.2, migrations/002_tests.sql на этапе 3.1. Общий мигратор создаёт schema_migrations один раз. Номера здесь — будущие имена, не команда переименовать существующие файлы. Если на сервере уже применена 001_tests.sql или любая другая миграция, сохранить её имя и checksum, тематические изменения оформить следующим свободным номером после сверки схемы; уже созданные таблицы тестов повторно не создавать. Обновить карту номеров в обоих документах до реализации. Порядок включения функций остаётся тематические → тесты независимо от исторического порядка применённых SQL. Сейчас миграции не создаются и не применяются.

- Явный мигратор без импорта боевого app и без загрузки `.env`; путь БД/контента задаётся явно. Режим audit/dry-run по умолчанию; применение только явным флагом после согласования.
- Версионированные SQL, checksum в schema_migrations, preflight версии SQLite/свободного места/backup/legacy-схемы/архива. Повтор применения завершённой версии — безопасный no-op; изменённый checksum уже применённой версии — отказ.
- Добавочные таблицы/индексы, транзакция и явный commit; тесты атомарности DDL именно выбранного механизма sqlite3, не предположение об автокоммите executescript.
- FK включается на каждом соединении после согласованной обработки legacy-проблем. Не отключать FK ради прохождения проверки и не удалять сироты автоматически.
- Ошибка до commit → rollback. После аварии определить по schema_migrations и фактической схеме, что применилось; не перезапускать вслепую.
- JSON: сначала валидация, запись во временный файл в том же каталоге, flush/атомарная замена. Для нескольких файлов — журнал файловой операции/manifest и техническая пауза; SQL и файловая система не являются одной ACID-транзакцией.
- Миграция старой перенумерации не включается в новые 001/002 и не выполняется повторно.

### 4.4 Откат

До открытия записи можно вернуть код, БД, JSON, медиа и архив из одного проверенного комплекта. После открытия нельзя просто восстановить вчерашнюю БД: будут потеряны новые ответы. Предпочтение — выключить feature flag, запретить новые старты/редактирование, сохранить данные и исправить вперёд. При необходимости полного восстановления сначала снова пауза и свежая копия текущего состояния, затем отдельное решение о переносе/потере новых данных.

Для тестов флаг начала отделён от чтения/продолжения: при откате UI новые старты закрыть, но активные попытки по возможности обслуживать совместимой версией service/worker до завершения. Не выключать worker и бросать active. Если безопасное обслуживание невозможно — согласованная аварийная процедура с фиксацией affected IDs и выдачей дополнительных попыток, без изменения старых ответов/таймеров задним числом.

Для тематических вариантов при откате закрыть новые старты и правки, сохранить версии, active и историю. Если для безопасности применяется явное скрытие, записать интервал блокировки и закрыть его при восстановлении доступа; обычная техническая пауза сама по себе не считается скрытием. Не откатывать схему удалением thematic_* после появления пользовательских ответов.

## 5. Последовательность этапов

Утверждённый приоритет: **0 — среда/backup/безопасность → 1 — тематические варианты и отдельный конструктор → 2 — восемь наборов через конструктор → 3 — тесты → 4 — теория и общая регрессия**. Подэтапы ниже выполняются последовательно и с отдельным подтверждением. Отсутствие материалов преподавателя не означает разрешение молча поменять приоритет или опубликовать фиктивные варианты.

Разработка и проверки — на изолированном стенде. Production-миграции/публикация имеют отдельные точки допуска: 1.6 для тематических, 3.6 для тестов. Названия 001_thematic.sql/002_tests.sql относятся к свежему журналу; при уже применённых миграциях действует раздел 4.3. Тематический модуль не зависит от таблиц или сервисов тестов.

### Этап 0.1. Среда и фиксация технических решений

- **Цель:** подтвердить production Python/SQLite/WSGI, журнал миграций, возможности worker для будущих тестов, нагрузку, пути private media и правила backup.
- **Существующие:** чтение app.py, requirements.txt, Procfile, scripts/DEPLOYMENT.md; изменения только этих двух документов до начала реализации.
- **Новые:** нет.
- **БД:** только read-only инвентаризация схемы/журнала; не импортировать app.py ради проверки.
- **Зависимости:** подтверждение обновлённого плана.
- **Риски:** production отличается от локальной БД/перенумерации.
- **Проверки/готовность:** зафиксированы реальные номера миграций и инфраструктура; продуктовые решения из этого запроса больше не считаются открытыми.
- **Откат:** эксплуатационных изменений нет.

### Этап 0.2. Backup и проверка восстановления

- **Цель:** восстановить полный согласованный комплект БД/JSON/медиа/архива до изменения схемы.
- **Существующие:** scripts/DEPLOYMENT.md; изоляция по образцу tests/test_homepage_integration.py и tests/test_ege_renumber.py.
- **Новые:** scripts/backup_platform.py, scripts/verify_backup.py, tests/test_backup_restore.py. Копии вне webroot/репозитория.
- **БД:** SQLite backup API, восстановление только во временную БД; исходная схема прежняя.
- **Зависимости:** 0.1.
- **Риски:** WAL, неполные media, несогласованный архив перенумерации, нехватка места.
- **Проверки/готовность:** раздел 4 полностью пройден, известны время восстановления и результат integrity/FK-проверок; `.env` и уведомления отключены в тестах.
- **Откат:** исходные данные не меняются.

### Этап 0.3. Необходимая безопасность и общая инфраструктура

- **Цель:** убрать препятствия безопасному подключению новых модулей без переписывания платформы.
- **Существующие:** app.py (get_db, bootstrap/init_db, JSON-auth, удаление пользователя, вывод пароля, пути uploads), templates/constructor_theory.html и constructor_uroki.html (опасная интерполяция); make_admin.py только при необходимости явного bootstrap. Конструктор полноценных вариантов не менять.
- **Новые:** core/{__init__,db,access,uploads}.py, scripts/init_database.py, tests/test_security_boundaries.py, tests/test_db_lifecycle.py.
- **БД:** без новой бизнес-схемы; до включения FK — отчёт о legacy-сиротах на копии, никаких автоматических удалений.
- **Зависимости:** 0.2; обработка найденных сирот требует отдельного решения.
- **Риски:** глобальная авторизация/foreign_keys нарушит гостевые маршруты и delete_user.
- **Проверки/готовность:** CSRF HTML/JSON/FormData, роли и owner, safe next, XSS/path, удаление фиктивного пользователя; импорт не пишет в боевую БД и не печатает секреты.

## 6. Тематические варианты: обязательная архитектура первого направления

Этот раздел содержит утверждённые правила тематических вариантов. Их нельзя заменять правилами тестов. Никакие операции здесь не реализуются при обновлении документации.

### 6.1 Данные и границы модуля

SQLite — единственный источник состояния тематического каталога, черновиков, версий и попыток. Общий банк `tasks/task_XX/tasks.json` читается для конструктора, но не изменяется. Отдельные `thematic_variants/*.json` как параллельный источник истины больше не планируются. Преподаватель создаёт первые восемь наборов через готовый конструктор, не через seed/импорт выдуманных задач.

Разделять четыре идентификатора:

- variant_id — тематический вариант, не номер полноценного варианта;
- position — порядок вопроса в опубликованной версии (1…N);
- source_task_num/source_task_id — ссылка на исходную задачу банка; номер 1–27 может повторяться;
- item_id — конкретный вопрос неизменяемой тематической версии.

**Одинаковая пара source_task_num/source_task_id не может повторяться в одном варианте.** Это серверная валидация черновика/публикации и UNIQUE в опубликованных items, а не только disabled-кнопка. Две разные задачи одного номера разрешены. Совпадающий числовой source_task_id у разных номеров не является дублем. Автоматическое связывание троек 19–21 из старого конструктора не переносится: каждый выбранный исходник — отдельный элемент.

Количество задач произвольное, без требования 20/27. При публикации нужен непустой список, валидные название/условия/эталоны и все используемые файлы; неполный черновик разрешён и ученикам не выдаётся. Лимиты байтов запроса/ресурсов не являются педагогическим ограничением количества задач.

### 6.2 Таблицы, FK и индексы

Время — INTEGER UTC milliseconds; DTO — ISO 8601 UTC, длительность в секундах, локальное отображение Europe/Moscow. Все перечисленные обязательные поля NOT NULL; nullable обозначены отдельно. Enum/булевы поля имеют CHECK. Внешние ключи включены на каждом соединении после проверки legacy-сирот. ID таблиц — INTEGER PK, source IDs проверяются по серверному банку, но не имеют SQL FK в JSON.

Версии/items/их media-связи никогда не обновляются по изменениям банка. Их FK не каскадируют при административном удалении варианта: родитель tombstone и версии остаются. Черновик можно удалить при удалении варианта. Удаление учётной записи ученика — отдельная существующая операция с явной очисткой его attempts/answers, не команда удаления варианта. Политика общей очистки исторических версий после удаления всех пользователей не вводится в этот релиз; пока существуют сохранённые результаты, media удалять нельзя.

### 6.3 Черновик и публикация неизменяемого снимка

Конструктор — отдельные routes/templates/JS; `templates/constructor_from_base.html` и `templates/constructor_editor.html` не меняются. Утверждённый `prototypes/thematic/editor.html` является эталоном, включая раздельное сохранение/публикацию и предупреждение о действующей версии. Банк показывает полное исходное условие с изображениями, таблицами и кодом до добавления. Список справа имеет удаление/перестановку, без ограничения количества.

PUT draft выполняет CAS по expected_revision и проверяет уникальность source-пар даже для неполного черновика. GET/PUT черновика доступны только администратору. Все тексты выводятся безопасно; код не исполняется. Сервер не принимает эталоны/пути как доверенные данные клиента при выборе source: загружает реальный исходник из банка.

Снимок создаётся **при публикации**, не при старте ученика:

1. Проверить admin, revision черновика и state не deleting/deleted; зафиксировать точные прочитанные байты source JSON и файлов. Для одинакового содержимого использовать content hash; не сохранять ссылку на изменяемый файл банка как историческое изображение.
2. Подготовить неизменяемые копии media в private data/thematic/media/, проверить реальный формат/размер/пути и наличие всех файлов. Если источник меняется во время чтения, повторить согласованное чтение/отклонить публикацию с конфликтом; копия/хэш должны относиться к реально сохранённым байтам. Декодирование/копирование не держат SQLite write-lock.
3. В BEGIN IMMEDIATE повторно проверить variant/draft revision и состояние, затем создать новую version, items с полными snapshot_json и media-связями, переключить current_version_id; сохранить receipt публикации и увеличить revision каталога. Старые версии не изменять. Если в это время вариант удалён — отказ без новых DB-ссылок, оставшиеся staging-файлы убрать позднее.
4. Если вариант был hidden, закрыть открытый интервал блокировки в том же commit; публикация возвращает доступ. Active-попытки при этом остаются на прежней version_id. Новые старты используют новую current_version_id.

Обычное сохранение черновика ни версии, ни видимости, ни временных интервалов не меняет. Возврат скрытого варианта без изменения содержания также возможен отдельным действием «Опубликовать/Показать действующую версию»: оно закрывает интервал, но не создаёт ложную новую content-version. Оба действия явно разделены на сервере (publish против visibility), даже если формулировка кнопки похожа.

Повтор публикации с тем же request_key возвращает прежнюю version_id. Неудачная операция оставляет текущую публикацию целой. Мусорные media чистятся только при отсутствии ссылок из всех версий и сохраняемых черновиков, без удаления файла, нужного истории. Подготовленные файлы черновика учитываются в его document_json; новые поля UI загрузки задач/изображений не добавляются.

### 6.4 Каталог и лучший результат

На `/variants` вкладки «Полноценные варианты» (по умолчанию) и «Тематические варианты». 20 полноценных JSON, конструктор и оба прежних режима не изменяются. Тематические сортируются по преподавательскому sort_order, затем id; PUT order защищён catalog revision и валидирует точный набор не удалённых ID.

Ученический каталог содержит только state=published. Карточка: название/описание текущей версии, её N, статус, лучшая завершённая попытка, прогресс active. Если active относится к старой версии, её прогресс показывает собственное N с пометкой версии, а не новое N карточки. При active и завершённых попытках одновременно видны оба показателя.

Приоритет статуса: active → «В процессе», иначе есть finished → «Пройден», иначе «Не начат». У тематических нет «Ожидает ручной проверки». Прогресс active = число непустых сохранённых ответов / N её версии; дополнительно можно показывать количество проверенных только после согласования визуального экрана, не путать его с ответами/итогом.

**Лучший тематический результат:** максимальный correct_count по всем finished и всем версиям; при равенстве — максимальная дробь correct_count/total_count. Дроби сравнивать без округления. При полном равенстве для стабильного отображения выбрать более позднюю submitted_at/id (числа результата одинаковы). Например, 15/20 лучше 10/10; при 10 правильных 10/10 лучше 10/20. Это не критерий тестов, где главный показатель — процент. В карточке best показывать S/N и процент именно выбранной версии. Нет finished → «—», active не участвует.

### 6.5 Прохождение, autosave и бинарная проверка

Только обычный режим, без временного лимита/дедлайна и квот повторений. Авторизованный ученик начинает published-вариант. Start в BEGIN IMMEDIATE проверяет state и существующую active, затем возвращает её либо создаёт новую со snapshot version_id и строками ответов. UNIQUE(user,variant) WHERE active закрывает гонку двух стартов. Даже новый request_key при найденной active закрепляется за ней в operation_keys, чтобы его replay после finish не создал следующую. Незавершённую нельзя сбросить: её продолжают. После finished можно создавать неограниченное число новых попыток, каждая имеет свой attempt_id/no.

Autosave — серверный, по item_id/expected_revision/mutation_id. Тип ответа соответствует immutable snapshot. Удаление ввода тоже сохраняется. UI использует debounce/последовательную очередь и индикатор сохранения; flush при смене задачи и перед finish. Неизвестный item_id/неверный тип/повтор source на уровне конструктора отклоняется сервером. Противоречащие изменения двух вкладок/устройств дают 409 с актуальной revision, не last-write-wins. Единственная active не означает внедрение отдельной тематической writer-сессии: CAS достаточно, механизм токена тестов сюда не добавляется.

Кнопка «Проверить» может атомарно сохранить последнее значение с expected_revision и проверить его либо проверить конкретную уже сохранённую revision. В ответе только правильность, revision и время сохранения: никаких эталонов, частей правильного набора, решения или первичных баллов. Для пустого ввода предложено не отправлять check и показать валидацию «Введите ответ»; на finish пустое всегда «Пропущено». Изменение проверенного ответа сбрасывает checked_revision/is_correct/checked_at, иначе старое «Правильно» станет относиться к новому тексту. Проверки и изменения не ограничены по числу, лишь технический rate limit против злоупотребления.

Grader thematic — отдельный чистый адаптер форматов текущего банка (строка, набор, таблица и другие реально поддержанные форматы). Для сложного ответа результат true только при правильности **всех** требуемых частей; прежний `get_points_for_task()>0` использовать нельзя. Номер темы берётся из source_task_num, не position. Семантика допустимого текстового ответа берётся из snapshot исходной задачи; строгое сравнение строк из системы тестов не переносится автоматически. grader_version фиксируется в опубликованной версии; версия реализации с такими правилами сохраняется для active/истории, при изменении алгоритма нужна явная новая версия правил, не массовая переоценка старых результатов.

Finish в одной транзакции проверяет владение/state видимости, применяет финальный пакет ответов с CAS (либо полностью отклоняет пакет), затем **заново проверяет все последние ответы**, включая никогда не проверенные и изменённые после check. Пустые → skipped/0, остальные → correct/1 либо incorrect/0. Записывает frozen answers/status, correct_count, total_count, submitted_at, elapsed_ms и state=finished. Перепроверка никогда не доверяет присланному is_correct и промежуточному кэшу. Повторный finish не создаёт второй результат и не меняет submitted_at. Эталон разрешён только на finished-result, не из активного DTO/snapshot-json.

### 6.6 Время и несколько циклов скрытия

Обычное время идёт от started_at до submitted_at, включая уход со страницы/закрытие/ночной перерыв. Исключаются только интервалы скрытия преподавателем. Общая техническая пауза не исключается автоматически, если не выполнено явное действие скрытия; не смешивать её с правилами тестового таймера.

Hide и show/publish выполняются в BEGIN IMMEDIATE. Переход published→hidden создаёт один интервал [hidden_at,NULL); повторный hide идемпотентен и не создаёт второй. hidden→published закрывает visible_at; повтор show не прибавляет время. Все события используют серверное время после получения блокировки. Первая публикация draft не создаёт скрытый интервал задним числом. Все интервалы сохранены, не только последняя дата скрытия.

Для попытки A=[s,e), blocked_ms = сумма max(0, min(e, end_i) − max(s, start_i)) по неперекрывающимся скрытым интервалам её variant_id. Для открытого интервала end_i=e (либо текущий server_now при показе active). elapsed_ms=max(0,e−s−blocked_ms), elapsed_seconds=floor(elapsed_ms/1000). Для finished сохранить elapsed_ms: последующее hide/show не меняет прежнее время. Старые версии используют интервалы того же variant_id. Защитить последовательность времён от отрицательных значений; production-часы синхронизировать.

Когда hidden: нет карточки/новых стартов; собственная active недоступна для условий, autosave, check и user-submit, возвращается 423 VARIANT_HIDDEN (короткое служебное сообщение без условий/эталонов). Сохранённые ответы и версия остаются. После show/publish та же active продолжается на своей версии. **Finished доступна владельцу и администратору и во время hidden, включая правильные ответы и исторические media.**

Гонка hide/save или hide/finish определяется порядком write-транзакций: закоммившееся до hide принято; после hide запрещено. Поздний пакет не принимается с клиентской меткой «вводил до скрытия». На скрытой открытой странице оставить несохранённый ввод только локально и явно сообщить, что он ещё не записан; после возврата доступа запросить актуальную revision, не перетирать сервер автоматически.

### 6.7 Удаление с сохранением результатов

Удаление тематического варианта — не физический CASCADE versions/attempts и не тестовое уничтожение истории. После предупреждения/подтверждения администратора:

1. В BEGIN IMMEDIATE проверить роль, expected_revision и request_key; установить внутреннее deleting в этой же транзакции. Все команды start/save/check/finish/publish/hide/order заново проверяют состояние после получения блокировки. Никаких промежуточных commit.
2. Зафиксировать общий cut-off t_delete. Если есть открытый hidden-интервал, закрыть его этим временем. Все active финализировать системно с finish_reason=variant_deleted: проверить последние **сохранённые** ответы заново, пустые skipped, посчитать elapsed с вычетом скрытых интервалов. Системной финализации разрешено обойти только блокировку hidden, не проверки целостности/версии. Клиентский несохранённый ввод не принимать.
3. Удалить изменяемый draft, очистить current_version_id, поставить deleted/deleted_at, увеличить catalog revision и сохранить receipt. Сохранить tombstone variant_id, versions/items/эталоны, законченные attempts/answers, visibility и все media-связи, нужные результатам. В административном списке/конструкторе и ученическом каталоге объект исчезает; просмотр истории остаётся. Восстановление варианта как продуктовая функция не добавляется.
4. Commit — единая точка удаления из активной системы и финализации. На ошибке rollback возвращает ВСЁ, включая прежнюю видимость, открытый интервал и active. Пока write-lock удерживается, конкурентные запросы ждут ограниченно и получают 503 при таймауте, а не частично удалённое состояние. После commit start/save/check получают 410 VARIANT_DELETED; собственная finished/result продолжает открываться. Повтор user-finish уже системно законченной попытки возвращает готовый результат, не применяя присланный пакет.

Если конкурентная запись успела commit до удаления, её ответ участвует в финализации; если нет — не участвует. Повтор DELETE с тем же ключом возвращает прежний receipt. Публикация, подготовившая файлы до удаления, повторно проверяет state и не воскрешает объект. Операция без внешней сети/файлового удаления внутри транзакции; media остаётся в истории. Для очень большого числа active измерить длительность на стенде: запрещено тайно разбивать удаление на независимо коммитящиеся куски. Если целевой объём не укладывается в окно блокировки, до реализации такого объёма согласовать отдельный надёжный процесс удаления; базовый релиз использует описанную атомарную транзакцию.

### 6.9 Общая история и восемь первых вариантов

`core/history.py` объединяет чтение legacy user_results и thematic_attempts(state=finished) без копирования строк между таблицами. Элемент истории имеет type=full/thematic и составной адрес (type,id), чтобы численно совпадающие ID не вели в другой раздел. Сортировка — по нормализованному времени, не строке dd.mm.yyyy. Full сохраняет свой secondary_score; thematic показывает correct_count/total_count, процент, elapsed и номер/название версии. Отдельная ссылка ведёт в правильный result-route.

История доступна ученику через существующую историю решений и преподавателю на странице ученика; все тематические finished, в том числе системно завершённые при удалении, сохраняются отдельно. Можно использовать пометку «Завершено при удалении варианта», не менять результат. Тестовые попытки в этот адаптер не включаются: они имеют собственный каталог/latest-result и административную вкладку «Тесты».

Лучший и средний **балл ЕГЭ** считаются только по legacy full. Значение верхнего счётчика «Решено вариантов» (все finished или только full) не уточнено новым запросом; до отдельного выбора предлагается оставить прежний full-смысл и явно подписать его, не называть это утверждённой сменой дизайна. Решение вынесено в раздел 8. Тематическая история добавляется в существующую «Историю решений», не в отдельную шестую вкладку; при последующем внедрении пяти вкладок тестов она остаётся на месте.

Первые 8 создаёт преподаватель в конструкторе после этапа 1.6: в каждом 20 включений, по две **разные** source-задачи каждого номера 1–10. Это требование к конкретному комплекту, не общий лимит/валидация публикации всех тематических вариантов. Порядок 1–8 задаётся вручную, сложность подтверждает преподаватель. Подбор сейчас не выполняется, фиктивные опубликованные записи запрещены.

## 8. Действительно нерешённые вопросы

Утверждённые правила конструктора, бинарной проверки, повторов номеров, времени, скрытия, удаления, истории и выбора лучших результатов повторного согласования не требуют.

### Перед соответствующими этапами

- **Среда (0.1):** hosting/worker, ожидаемая конкуренция, допустимая длительность атомарного удаления большого набора; расписание backup, хранение, RPO/RTO и окно обслуживания. Предложение: независимый worker и проверка нагрузки на копии до выбора численных лимитов.
- **Безопасность (0.3):** объём устранения старой выдачи эталонов exam/reshenie, повторных сохранений legacy-результатов и изоляции tracer; библиотека декодирования, если текущих средств недостаточно. Предложение: обязательные общие guards и безопасные новые модули, отдельное согласование изменений старых механизмов; без установки зависимостей сейчас.
- **Тематические экраны (1.1):** визуальное утверждение каталога, прохождения и результатов. Конструктор уже утверждён. Это отдельная приёмка, не повод переделывать его дизайн.
- **Общий показатель «решено вариантов» (1.5):** считать только полноценные либо все завершённые, включая тематические. До согласования сохранить прежний смысл. Лучший/средний балл ЕГЭ в любом случае исключают тематические, история их включает.
- **Первые восемь (2):** преподаватель выбирает 160 включений задач и возрастающую сложность. Ограничение 20 и по две задачи 1–10 относится только к этому комплекту.
- **Сессия тестов (3.1–3.3):** одна active на конкретный тест (предлагается) либо глобально; подтверждение переноса пишущего клиента при смене устройства/F5. Сохранение ответов и исходного дедлайна обязательно в обоих вариантах.
- **Квоты тестов:** предлагается расходовать попытку на старте, grants выдавать отдельно; согласовать изменение квоты между версиями и компенсации технических сбоев.
- **Настройка эталонов тестов:** предлагается фиксировать в версии/попытке, альтернатива — явное ретроактивное изменение политики. В обоих случаях выдавать только после полной проверки и только последней попытке.
- **Оценки тестов:** предлагается пустой manual сразу оценивать 0; решить, может ли администратор дать 1 пропуску. При равном лучшем проценте предлагается выбирать более позднюю полностью проверенную попытку.
- **Технические границы тестов:** максимальные длины/количество вопросов/размеры и время, правила LF/CRLF при строгом сравнении. Регистр и пробелы не нормализуются. Утвердить численные ограничения перед серверной валидацией.
- **Теория (4):** точные примеры №2, удаляемый вид №5, материал/иллюстрация DPI; примеры №8/9; номер IP-раздела на production и две схемы. Без материалов не подменять содержательные решения преподавателя.

Проверка пустого ответа в тематическом режиме: предложение — отключить «Проверить» и попросить ввод; альтернатива — ответ «Неправильно». При завершении пустой ответ в любом случае «Пропущено». Это маленькое UX-решение входит в визуальное согласование 1.1.
