# Перенос «Поехали!» без замены SQLite

Пакет сохраняет тест `611958516266134` в текущем состоянии **published**:
актуальная версия `4384689890600735`, предыдущая `1826707312248266`.
В каждой версии 25 вопросов. Текущий документ: 1800 секунд, одна попытка,
показ эталонов выключен; 43 варианта выбора, 18 отмеченных правильными,
9 строк-эталонов, 17 вопросов с автоматической и 8 с ручной проверкой.
Преподаватель изменил отметки правильности после первоначального восстановления;
этот релиз не возвращает старые ответы. JSON и статус при подготовке не менялись.

## Что делает процедура

`python -m scripts.register_test_content` по умолчанию только проверяет.
Она не импортирует `app.py`, не читает `.env`, не выполняет миграции, не пишет JSON.
SQLite хранит стабильные ID и хеши версий; публикация и черновик читаются из JSON.
Штатный `Store` проверяет связи, содержимое, состояние и хеши версий.

Перед записью процедура проверяет историю миграций, integrity/FK, конфликты ID,
состав старого каталога и побайтовую сохранность его файлов. Если сервер содержит
другие тесты, отсутствующие в пакете, или изменённые JSON, перенос запрещён.
Нужно отдельно подготовить согласованный пакет с сохранением серверного контента;
просто заменять `catalog.json` нельзя. Существующий ID принимается только при
совпадении старого JSON или наличии квитанции именно этого переноса.

Регистрация сначала исполняется на SQLite Backup API копии в памяти с включёнными
FK и триггерами. Сравниваются все таблицы: разрешены только новые ID выбранного
теста, его версий, вопросов, вариантов и одна квитанция в `content_commits`.
Существующие строки, пользователи, прогресс, попытки, ответы, оценки, другие
тесты и их счётчики должны остаться неизменными. Затем создаётся резервная копия
SQLite и JSON с проверкой восстановления; запись проходит одной транзакцией под
блокировкой контентного хранилища и `BEGIN IMMEDIATE`. Повтор даёт
`already_registered` без новых строк. Любое исключение откатывает транзакцию.
Тесты с медиа требуют отдельной процедуры; у «Поехали!» медиа нет.

## Действия владельца на REG.RU

Эти команды подготовлены по путям из `PRODUCTION_TESTS_WORKER.md`.
Агент их на сервере **не выполнял**. Команды запускаются последовательно в одной
SSH-сессии владельца. При ненулевом коде любого шага остановиться, не продолжать.
Обновление требует действующего согласованного режима обслуживания: остановить
запись Passenger/worker/cron на время снимка, установки и регистрации. Эта инструкция
не меняет их конфигурацию и не заменяет существующий порядок обслуживания.
Не запускать `app.py` между установкой файлов и регистрацией.

```sh
set -eu
umask 077
SITE=/var/www/u3541405/data/www/egevolution.ru
PY=/var/www/u3541405/data/egevolution-venv312/bin/python
BACKUPS=/var/www/u3541405/data/egevolution-backups
cd "$SITE"
test -f users.db
test -z "$(git status --porcelain --untracked-files=no)"
git fetch origin main
# Подставить полный хеш именно из отчёта этого выпуска, не произвольный новый main.
RELEASE_SHA=COMMIT_FROM_RELEASE_REPORT
git cat-file -e "$RELEASE_SHA^{commit}"
git merge-base --is-ancestor "$RELEASE_SHA" origin/main
git merge-base --is-ancestor HEAD "$RELEASE_SHA"
WORK=$(mktemp -d "$BACKUPS/test-transfer-XXXXXXXX")
mkdir "$WORK/release"
git archive --format=tar --output="$WORK/release.tar" "$RELEASE_SHA"
tar -xf "$WORK/release.tar" -C "$WORK/release"
cd "$WORK/release"
"$PY" -B -m scripts.register_test_content --pysqlite3 \
  --database "$SITE/users.db" --content-root "$WORK/release" \
  --previous-content-root "$SITE" --test-id 611958516266134 \
  --backup-directory "$WORK/before-update"
```

Ожидается `ready` (либо `already_registered` для повторного переноса),
`publication_state: published`, `questions: 25`, `versions: 2`,
`current_version_id: 4384689890600735` и `restore_verified: true` в
`$WORK/before-update/verification.json`. Если версия/состояние неожиданны,
остановиться и сверить выбранный GitHub-коммит с отчётом выпуска.

При успешной проверке установить **тот же проверенный коммит**, затем зарегистрировать:

```sh
cd "$SITE"
git merge --ff-only "$RELEASE_SHA"
"$PY" -B -m scripts.register_test_content --pysqlite3 \
  --database "$SITE/users.db" --content-root "$SITE" \
  --previous-content-root "$WORK/before-update" --test-id 611958516266134 \
  --apply --confirm-offline --backup-directory "$WORK/before-registration"
"$PY" -B -m scripts.register_test_content --pysqlite3 \
  --database "$SITE/users.db" --content-root "$SITE" \
  --previous-content-root "$WORK/before-update" --test-id 611958516266134
```

Ожидается `registered`, затем `already_registered`. Команда с `--apply` тоже
безопасна при повторе: квитанция привязана к ID и содержимому теста. SQLite сервера
не заменяется локальной БД. При отказе после установки файлов оставить обслуживание
включённым и сохранить диагностику/снимки; не запускать приложение для обхода проверки
и не восстанавливать всю БД поверх новых результатов.

После успешной регистрации владелец возвращает приложение/worker по действующему
порядку, проверяет вход, каталог, `/admin/tests/611958516266134/edit`, 25 вопросов,
настройки, ответы и оба состояния черновика/опубликованной версии. Повторная
публикация «Поехали!» для переноса не нужна. Сохранение/публикацию проверять на
отдельном тесте. Приёмка native Linux/pysqlite3 остаётся за владельцем; Windows
проверки не доказывают работу именно серверной сборки SQLite 3.26.0.

## Отдельное решение для истории миграции 003

По решению владельца в этот релиз **не входит** локальное восстановление последней
пустой строки `003_json_content.sql`. Опубликованный SQL остаётся побайтово прежним:
SHA-256 `1bdd389b5ba0530ee61312376ca88db785ebf3decbef537b524f0516827d7431`.
Локальная рабочая БД ожидает сохранённый исторический артефакт:
`9dce7b7eb5a73084b71ce6f6ef0f872c51332afbc1eb6df50b39b574606bf3fc`.
Локальная правка и её тест остаются вне коммита, поэтому локальный запуск не ломается.

Регистратор не принимает альтернативную checksum и не исправляет ledger. Если
сервер ожидает `9dce…`, проверка остановится **до обновления сайта**. Следующий
отдельный этап: получить read-only аудит серверного ledger и фактической схемы,
сопоставить сохранённые SQL-артефакты из Git и проверенных backup; после отдельного
согласования выбрать единый исторический baseline и документированный перенос
истории с восстановимой копией. В этом релизе такая запись не разрешена и не
реализована. Нельзя заменять checksum вручную, удалять историю или отключать аудит.

`users.db`, `.env` и локального теста checksum. SQL 003 в этом дереве имеет
опубликованный SHA-256 `1bdd389b…`. На временных фиктивных БД выполнены:

- Полный Python-набор: 255 тестов, 254 успешно, один ожидаемый пропуск native Linux
