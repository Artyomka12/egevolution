# Тематические варианты: этап 1.2

Реализованы только добавочная схема, автономный мигратор и чистые функции
предметной области. Flask, маршруты, текущий get_db(), интерфейсы и конструкторы
не подключаются к новым таблицам. Импорт features.thematic не открывает БД.
Рабочие users.db и .local-data/dev-users.db не мигрированы.

## SQLite и предпосылки

Цель — SQLite 3.26.0. Используются CREATE TABLE/INDEX/TRIGGER, CHECK, составные
FK и частичные UNIQUE-индексы. Нет JSON1, STRICT, generated columns, RETURNING,
UPDATE FROM, новых функций времени и динамических выражений сообщения RAISE.
JSON валидируется Python. Время хранится в UTC миллисекундах INTEGER.
Источники для проверки доступности SQL:
[SQLite 3.26.0](https://www.sqlite.org/releaselog/3_26_0.html),
[внешние ключи](https://www.sqlite.org/foreignkeys.html),
[триггеры](https://www.sqlite.org/lang_createtrigger.html).

Автотесты выполняются SQLite установленного Python. Они не заменяют отдельный
прогон на движке ровно 3.26.0 до серверного выпуска. Никакие библиотеки ради
смены SQLite в этой задаче не устанавливаются, REG.RU не используется.

Схема расширяет платформу, поэтому требует users(id INTEGER PRIMARY KEY).
Полностью пустой файл без базовой схемы отклоняется с понятной ошибкой:
мигратор не импортирует app.py и не создаёт пользователей. Тест «пустой базы»
использует пустые legacy-таблицы из CREATE TABLE текущего init_db(), извлечённые
через AST, и одного фиктивного пользователя. Реальные записи не копируются.

## Данные и неизменяемость

11 thematic-таблиц соответствуют разделу 6.2 плана; schema_migrations — общий
журнал, создаваемый мигратором в той же транзакции. Единственная начальная
строка — thematic_catalog_state(1,1); фиктивных вариантов/попыток нет.

Дополнительное внутреннее поле thematic_versions.sealed — защёлка сборки:
repository.store_version() одной транзакцией создаёт version/items/media-связи,
проверяет количество и позиции и переводит sealed из 0 в 1. Только запечатанная
версия может стать current_version или основой попытки. Запечатанную версию
нельзя дополнять/редактировать/удалять. Это не новый статус интерфейса.
Атрибуция автора допускает SET NULL при удалении его аккаунта.

make_snapshot() отделяет условия, эталоны, параметры таблиц/кода и подписи от
исходного JSON. Снимок содержит schema/grader version и контрольные суммы.
Материалы требуют соответствующих immutable media_id/sha256; репозиторий
проверяет их наличие и совпадение хэша. Подписи/порядок принадлежат версии.
Ссылки на изменяемые пути банка не используются как исторические материалы.
Физическое копирование и проверка файлов, авторизация, CAS публикации,
переключение видимости и маршруты относятся к 1.3 и здесь не реализованы.

save_draft() проверяет повторы source-пар и ревизию; неполный/пустой черновик
разрешён. Для версии нужен непустой список. Одинаковая source-пара запрещена
Python-валидацией и SQL UNIQUE. Номер ЕГЭ не равен position; разные исходники
одного номера разрешены, ограничения 20/27 нет.

Составные FK не позволяют подменить версию варианта/попытки/ответа. Одна active
на ученика/вариант гарантируется частичным UNIQUE. Много finished и версий
сохраняются отдельно. Таблицы и ограничения подготовлены; пользовательские
команды старта/autosave/check/finish, скрытие и системное завершение при удалении
относятся к 1.4 и не реализуются здесь. SQL ограничивает некорректные суммы,
неполное завершение, изменение версии/завершённого ответа и перекрытия скрытий.
Очистка данных при удалении аккаунта потребует явного порядка удаления в будущей
интеграции; автоматического каскада исторических versions/media нет.

## Бинарная проверка v1

Банк содержит 2928 задач: 2278 со строкой, 316 с парой, 334 с таблицей.
ordinary-binary-v1 сохраняет lower().strip() обычного режима для каждой строки.
Внутренние пробелы, порядок полей/строк/столбцов, количество ячеек значимы.
Числа не преобразуются из строк: «01» и «1» различаются. Пара/таблица получает
1 только за полное совпадение, иначе 0. Пустой ответ — skipped/0; непустой
ответ неверной формы — incorrect/0. Неверный эталон/неизвестная версия grader
вызывает ошибку, а не автоматический правильный/неправильный результат.
Номер ЕГЭ и ID не влияют на количество баллов. Код из условий не выполняется.

task_dto() отдаёт только разрешённые поля; при active нет эталонов и материалов
role=reference. Разрешение finished и проверка владельца будут обязанностью
сервиса/маршрута. best_attempt() сравнивает число правильных, затем точную дробь,
затем submitted_at/id; округлённый процент для выбора не используется.

## Мигратор

Без --apply выполняется только audit, подключение mode=ro. Требуется явный
--database; переменные окружения и .env не читаются. Пример, пока не запускать
применение на рабочих базах:

```powershell
$pythonExe = 'C:\Users\Артем\AppData\Local\Programs\Python\Python312\python.exe'
& $pythonExe -B -X utf8 scripts/migrate.py --database 'ПУТЬ_К_ВРЕМЕННОЙ_БАЗЕ'
```

Применение к временной базе дополнительно требует --apply, --confirm-offline
и --backup ПУТЬ. Backup должен быть отдельной SQLite-копией и совпадать логически
с источником под BEGIN IMMEDIATE. Проверяются integrity/FK, наличие users,
версия SQLite, свободное место, журнал/checksum и определения применённых
объектов. Неизвестная история, изменённый SQL, частичная схема и устаревший backup
останавливают операцию. Уже применённые миграции не переименовываются.

Runner исполняет отдельные завершённые SQL statements, не executescript();
DDL и запись журнала атомарны. Ошибка, включая ошибку последнего statement,
откатывает всё. Повтор завершённой миграции — no-op без повторного DDL.

На этапе 1.2 apply дополнительно запрещён для обеих рабочих локальных БД,
включая ссылки на них. Снятие этого предохранителя для dev-users.db — отдельная
согласованная операция после свежей копии и остановки писателей владельцем.
Мигратор сам не останавливает процессы. Backup SQL не заменяет полный комплект
БД/JSON/media/архива; перед последующим выпуском обязателен план backup/restore.
Откат этапа сейчас — не подключать модуль; в тестах временные файлы удаляются.
Для базы с реальными новыми данными не применять DROP/старую копию вслепую.

## Проверка и следующий шаг

```powershell
& $pythonExe -B -X utf8 -m unittest discover -s tests -p 'test_thematic_*.py' -v
```

Тесты используют только временные фиктивные БД. Банк читается без изменений.
Проверяются все текущие форматы, запрет частичных баллов, снимки и media,
160 задач, FK/UNIQUE/CHECK, CAS, исторические версии, два конкурентных соединения,
интервалы, безопасный audit, backup, повтор, откат и повреждённый журнал/схема.

Следующий функциональный этап — 1.3, отдельное управление/конструктор, только
после подтверждения. Перед любой миграцией dev-users.db нужно отдельное
подтверждение владельца; текущий Flask-сервер продолжает работать без изменений.
