# Учебный контент в JSON

Состояние на 15 октября 2026 года. Учебное содержание тематических вариантов и
тестов больше не хранится в SQLite. Теория, банк заданий и полноценные варианты
сохранили прежний формат.

## Файлы

```text
thematic_variants/
  catalog.json
  variant_<stable_id>/material.json
  variant_<stable_id>/versions/<stable_version_id>.json
  media/<sha256>
tests_content/
  catalog.json
  test_<stable_id>/material.json
  test_<stable_id>/versions/<stable_version_id>.json
  media/<storage_key>
```

Каталог содержит порядок, список материалов и описатели медиа. Файл материала
содержит состояние публикации, ссылку на текущую версию и черновик. Опубликованная
версия содержит неизменяемые задания, ответы, настройки и связи с изображениями.
Исходные ID сохранены; новые ID случайные, положительные, меньше 2^52 и безопасны
для JavaScript Number. Порядок вопросов определяется `position`, а не величиной ID.

Все JSON и медиа предназначены для Git, но не для прямой статической выдачи HTTP.
Пользователь получает только прежние отфильтрованные DTO; доступ к изображениям
проверяется серверными маршрутами. Локальные ID авторов исключаются из JSON;
владение загрузками тестов остаётся приватной записью SQLite.

## SQLite и сохранение

Сохранены прежние таблицы пользователей, доступа, прогресса и результатов.
Тематические рабочие таблицы: `thematic_attempts`, `thematic_answers`,
`thematic_visibility_intervals`, `thematic_operation_keys`.
Рабочие таблицы тестов: `test_attempts`, `test_attempt_answers`,
`test_grade_events`, `test_attempt_grants`, `test_operation_keys`.

Таблицы `thematic_variants`, `thematic_versions`, `thematic_version_items`,
`thematic_media`, `tests`, `test_versions`, `test_version_questions`,
`test_question_options`, `test_media` содержат только идентификаторы, связи,
контрольные суммы версий и приватное владение загрузками. Условий и эталонов в них
нет. `content_commits` содержит только маркеры завершённых файловых транзакций.

Конструкторы используют прежние API, CAS и ключи повторных операций. Общий
`core/content_store.py` проверяет JSON, берёт межпроцессную блокировку, начинает
SQLite-транзакцию и записывает журнал старых/новых файлов. Файлы заменяются
атомарно; SQLite-маркер определяет восстановление после аварии. Каталог
`.content-runtime` приватный и исключён из Git. Его нельзя удалять при работающем
приложении или незавершённом журнале.

Сохранение изменённого материала создаёт новую версию. Начатые попытки продолжают
использовать старую. Удаление тематического варианта сохраняет его историю;
удаление теста следует прежнему правилу удаления связанных результатов.
Отсутствующий/испорченный JSON или изменённая историческая версия блокируют
операцию с 503, а не подменяются пустым содержимым.

## Локальная миграция

Проверенная исходная копия:
`D:\EGEvolution-backups\json-content-20261015-115357`.

Непосредственный снимок перед переключением:
`D:\EGEvolution-backups\json-cutover-20261015-123112\users-before.db`.
В том же каталоге `cutover.json` фиксирует контрольные суммы и результат.

`003_json_content.sql` описывает целевую схему новой базы. Его нельзя выполнять
непосредственно на существующей базе. `scripts/migrate.py` проверяет эту схему,
но намеренно запрещает её применение на месте. Старые 001/002 не переписаны.

Экспортёр создаёт только новый независимый каталог и новую базу:

```text
python -m scripts.json_content_migration --source <проверенная-копия.db> --destination <новый-каталог-вне-источника> --media-source <корень-исходных-медиа>
```

Источник должен иметь проверенную схему 001/002. Экспортёр открывает его только
для чтения, делает согласованный SQLite backup в память, строит новую базу,
сверяет все сохраняемые записи и учебный контент после чтения JSON, копирует
медиа с проверкой SHA-256 и пишет `verification.json`. Он не устанавливает
результат на место исходника. Если выполнение оборвалось, оставшийся кандидат
нельзя считать проверенным: исходник сохранён, повторять следует в новом каталоге.

В локальном проекте переключение выполнено отдельно после тестов, при отсутствии
процессов приложения, с точной проверкой путей, исходного SHA, отдельным снимком,
проверкой восстановления и возвратом исходного файла при ошибке. Сохранены
8 опубликованных вариантов, 9 версий, 164 задания, 85 медиа и 122 связи.
Девятая запись материала — ранее удалённый вариант с историей, а не новая публикация.

## Запуск и перенос через Git

Обычный `python app.py` использует корневую `users.db`. По умолчанию JSON находятся
рядом с базой. Если база вынесена из каталога приложения, задайте
`EGEVOLUTION_CONTENT_ROOT` явно как корень проекта с двумя JSON-каталогами.
Те же значения должны использовать веб-процессы и отдельный worker.

На новом сервере понадобятся зависимости из `requirements.txt`, право записи
SQLite и `.content-runtime`, а для административного редактирования — также JSON
и медиа. Нельзя публиковать эти каталоги как открытый static/download directory.
`users.db`, `.env`, журнал восстановления и результаты не отправляются в Git.
Синхронизация с GitHub автоматически не выполняется.

Перед будущим переносом на REG.RU:

1. Отдельно согласовать обслуживание, остановку писателей и SQLite online backup
   серверной базы; проверить восстановление в изоляции. Серверная база не
   заменяется локальной базой с локальными пользователями.
2. На копии серверной базы проверить старые миграции и создать отдельный кандидат
   новой схемы. Если 001/002 отсутствуют, подготовить их на временной копии по
   прежнему безопасному процессу, сохраняя исходный снимок.
3. Сопоставить серверные исторические JSON и передаваемые через Git материалы по
   ID и контрольным суммам. При конфликте или исчезновении версии остановиться;
   не менять ID попыток автоматически и не перезаписывать историю.
4. Проверить все пользовательские записи, медиа, foreign_key_check/integrity_check,
   доступы и worker на кандидате. Затем отдельно согласовать точное переключение
   файлов и базы с проверенным откатом. Универсального автоматического
   установщика на рабочую базу нет.
5. После git pull регистрация новых идентификаторов выполняется из JSON без
   импорта локальных аккаунтов. Исторические версии удалять нельзя. Не запускать
   git pull одновременно с публикацией или незавершённой файловой транзакцией.

REG.RU в этой работе не подключался; его реальная база не проверялась.

Откат выполняется согласованным комплектом: исходный код и база из резервной
копии до рефакторинга. Возвращать только старую SQLite при новом JSON-backend
недостаточно — запуск остановится на проверке схемы. Перед откатом сохранить
сделанные после переключения пользовательские записи отдельным снимком.
