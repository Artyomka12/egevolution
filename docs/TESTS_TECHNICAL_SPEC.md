## 1. Границы и исходное состояние

Раздел реализуется в существующем Flask/Jinja-приложении и SQLite, без SPA, отдельного сервиса исполнения кода и переноса старых результатов. Подготовка документов не включает программирование, миграции или установку зависимостей.

Утверждённые файлы `prototypes/tests/` — неизменяемые визуальные эталоны. Их демонстрационные массивы, клиентский таймер и хранение в памяти не являются серверной архитектурой.

Не применять светлую базу к админке.

### 1.1 Подтверждено чтением текущего репозитория

- `app.py` содержит маршруты, доступ, sqlite3 и загрузчики JSON. БД — `users.db`. Импорт вызывает `init_db()` и может создать администратора: служебные проверки не должны импортировать приложение до изоляции БД и окружения.
- Есть Flask-WTF `CSRFProtect`, хэши паролей, параметризованные SQL. Администратор определяется `users.is_admin`; проверки повторяются в обработчиках.
- `user_results` и `user_task_answers` обслуживают варианты. Ответы связаны с попыткой через пользователя, номер варианта и дату до минуты. Такой механизм не подходит новым попыткам.
- `user_variant_progress` принимает клиентское `time_remaining`. Его нельзя использовать как серверный таймер тестов.
- `get_points_for_task()` и `convert_to_secondary_score()` содержат правила ЕГЭ, отличающиеся от 0/1.
- `templates/exam.html` и `templates/reshenie.html` сериализуют полный `tasks` через `tojson`. Для тестов нужен отдельный ученический DTO без эталонов.
- Статистика ученика: `admin_view_user()`, `load_user_stats()`, `templates/admin_user_stats.html`. Первые четыре раздела сохраняются; тесты не записываются в `user_results` и не меняют три прежних показателя.

## 2. Функциональные инварианты

1. Типы: `single_choice`, `multiple_choice`, `free_text`. У свободного ввода формат `singleline`/`multiline` и проверка `auto`/`manual`. Формат поля не создаёт четвёртый тип.
2. Максимум за вопрос — 1. Оценка только 0, 1 либо NULL до проверки. Частичных баллов нет.
3. Варианты содержат текст. Условие может содержать одно изображение, текст и безопасно отображаемый код. Код ученика и автора никогда не выполняется.
4. Single — один эталон. Multiple — непустое множество эталонов; 1 только при равенстве множеств ID. Порядок выбранных вариантов не влияет.
5. Auto free — несколько допустимых строк; сравнение без `trim`, `lower`, числового преобразования, Unicode-нормализации и подмены пробелов. Переносы и регистр значимы.
6. Manual free в согласованном конструкторе не требует эталона. Если его нет, интерфейс проверки показывает только ответ ученика.
7. После отправки ответы ученика неизменяемы. Коррекция меняет оценку и журнал, а не ответ.
8. Время, квоты, оценки, version_id, user_id и права определяет сервер, не клиент.
9. Начало фиксирует опубликованную версию и дедлайн. Редактирование или скрытие не меняет начатое прохождение.
10. Во время прохождения правильность, эталоны и баллы не выдаются через HTML, API или скрытые атрибуты.
11. Все пользовательские HTTP-мутации имеют CSRF, авторизацию, проверку принадлежности и транзакционную защиту. Системная финализация дедлайна использует тот же сервис/транзакции, но не требует пользовательского CSRF и не принимает пользовательские ответы.
12. Реализация каждого этапа начинается только после отдельного подтверждения.

## 4. Структура SQLite

Новая схема добавочная, legacy-результаты не перестраиваются. На проверенной локальной users.db таблица schema_migrations отсутствует, каталога migrations пока нет; для нового журнала планируются 001_thematic.sql, затем 002_tests.sql. schema_migrations создаётся общим мигратором при первом функциональном направлении, в миграции тестов не пересоздаётся. Если на production уже есть применённые миграции, сохранить их имена/checksum и выбрать следующий свободный номер по разделу 4.3 IMPLEMENTATION_PLAN.md; ничего не переименовывать задним числом. Внешне адресуемые ID тестов, версий, вопросов, попыток и media — INTEGER PRIMARY KEY AUTOINCREMENT: удалённые ID не переиспользуются, старые ссылки и idempotency receipts не могут адресовать новый ресурс; время — UTC Unix milliseconds INTEGER, отображение Europe/Moscow, API — однозначные ISO-строки. JSON валидируется приложением; наличие SQLite JSON-функций не предполагается без проверки окружения.

### 4.1 Каталог, черновики, версии

| test_media_links | test_id FK; media_id FK; PRIMARY KEY(test_id,media_id). Разрешённая сервером принадлежность media тесту, включая явно созданные связи при копировании; одного известного media_id недостаточно для привязки |

Опубликованные настройки, вопросы, варианты и эталоны неизменяемы. Администратор работает с копией в черновике. Нет API изменения опубликованной версии. Repository запрещает UPDATE её содержимого; это проверяется тестами. Допустимы защитные SQL-триггеры, если предусмотрена согласованная процедура удаления целого теста.

Принадлежность `tests.current_version_id` тому же test_id обеспечивается составным FK либо эквивалентным триггером. Межстрочные ограничения — один эталон single, наличие auto-строк, допустимый тип/режим, последовательность позиций — проверяются в транзакции публикации; один FK их не обеспечивает.

Обязательные поля — NOT NULL, кроме явно nullable; enum и булевы флаги имеют CHECK. Single/multiple допускают только grading_mode=auto; manual — только free_text. Для варианта выбора free_input_mode=NULL, для free_text значение обязательно. Админское исправление автоматической оценки не меняет grading_mode вопроса. При публикации запрещены одновременно опции и строки-эталоны одного вопроса. Вопрос содержит не более одной media-ссылки. Готовый media, включая alt_text и размеры, неизменяем: новая подпись/файл создают новую запись, иначе старые версии визуально изменятся.

| Таблица | Поля и ограничения |

| test_grade_events | id; attempt_id,question_id; old_score,new_score; old_source,new_source; actor_user_id nullable; actor_kind system/admin; occurred_at; request_key; result_revision. Без комментариев. UNIQUE(actor_user_id,request_key) для админских операций |
| test_attempt_grants | id; user_id,test_id; amount > 0; granted_by nullable; granted_at; request_key; UNIQUE(granted_by,request_key). Добавочная выдача, без перезаписи истории |
| test_operation_keys | actor_user_id; operation_scope; request_key; request_hash; resource_id; created_at; UNIQUE(actor_user_id,operation_scope,request_key). Не хранить bearer-токены/эталоны в кэшированном ответе |
| schema_migrations | version PK; checksum; applied_at; application_release. Отчёт мигратора содержит проверки и длительность |

Составные FK ответов связывают `(attempt_id,version_id)` и `(question_id,version_id)`; попытка связывает `(version_id,test_id)`. Вопрос другой версии не может попасть в ответ. Строки ответов создаются для всех вопросов при старте, включая пропуски. Знаменатель — число вопросов версии, а не число полей клиентского запроса.

Связи принадлежащих тесту записей допускают каскадное удаление только при подтверждённом удалении всего теста. Сначала в той же транзакции очистить current_version_id и draft.based_on_version_id, затем удалить дочерние записи/тест в определённом порядке. Media — RESTRICT до проверки всех ссылок, создатели/проверяющие — SET NULL при удалении администратора. Для учащегося удалить его попытки и grants вместе с учётной записью. Проверить эту процедуру отдельными FK-тестами; не рассчитывать на неявный порядок циклических каскадов.

Обнуление ссылки на удалённого автора — допустимое служебное изменение атрибуции, не изменение содержимого опубликованной версии/media. test_operation_keys.actor_user_id остаётся NOT NULL с FK ON DELETE CASCADE: удалённая учётная запись всё равно не имеет права replay. Удаление ученика не удаляет тест, созданный другим пользователем; удаление автора не уничтожает опубликованные версии и чужие результаты.

Индексы: частичный UNIQUE(user_id,test_id) WHERE state='active'; attempts(state,deadline_at), (user_id,test_id,state,submitted_at), (test_id,state); answers(attempt_id,score); tests(publication_state,sort_order,id); grants(user_id,test_id); events(attempt_id,occurred_at). Окончательно проверить EXPLAIN на синтетическом объёме.

Предложение: одна активная попытка на пару ученик–тест и один пишущий клиент этой попытки. Это не глобальный запрет одновременно решать разные тесты. Если нужен глобальный запрет, потребуется согласование и UNIQUE(user_id) WHERE active.

Результат вычисляется из answer.score. Если впоследствии понадобится кэш суммы, обновлять его вместе с оценкой и result_revision в одной транзакции и регулярно сверять. На первом релизе кэш не нужен. Правила тематических вариантов сюда не переносятся: у тестов лучший результат определяется процентом, скрытие не блокирует active, а удаление уничтожает попытки и результаты.

`operation_scope` включает имя действия и целевой ресурс (для ответа — attempt_id/question_id). Запись ключа и доменное изменение коммитятся вместе. resource_id содержит ID созданного/изменённого объекта; для save достаточно перечитать актуальную revision, но не повторять запись. Для start, вернувшего уже существующую active по новому request_key, также сохраняется соответствие ключа этой попытке. Это исключает создание следующей попытки при позднем replay такого запроса.

### 4.3 Удаления и исторические данные

- Скрытие теста запрещает новые старты, но не продолжение active и не просмотр разрешённого результата последней попытки. Блокировки времени тематических вариантов здесь нет.
- Утверждено: администратор может удалить любой тест, включая active, после предупреждения о потере всех попыток/результатов и подтверждения. Наличие active не является основанием отказа. Удаляются тест, черновик, версии, попытки, ответы, оценки, grants и связи media; автоматическая финализация для сохранения истории не выполняется. Это отличается от удаления тематического варианта.
- Медиа удаляется после commit только при отсутствии ссылок из других тестов, копий и черновиков. Ошибка уборки не отменяет сохранённые результаты.
- Удаление ученика явно очищает новые дочерние записи. Ссылку на администратора в журнале можно SET NULL с сохранением технической информации о событии. Политика хранения журнала после удаления согласуется.
- Включение FK требует проверки legacy-сирот и `delete_user()`: сейчас он не удаляет все таблицы прогресса/последних ответов. Не удалять сироты автоматически.

DELETE с expected_revision и request_key выполняется в BEGIN IMMEDIATE. Под той же блокировкой проверяются роль, подтверждение и ревизия, затем очищаются current_version_id/based_on_version_id, удаляются дочерние записи и сам тест, увеличивается revision каталога, записывается receipt удаления в test_operation_keys, не имеющий FK на удаляемый объект. Никаких промежуточных commit. Если save/start/submit/grade/worker успел закоммититься первым, его данные входят в удаляемое множество; если DELETE первый, последующая операция повторно проверяет наличие и получает 404 TEST_DELETED/NOT_FOUND. Ученику — одинаковый 404 без раскрытия чужих объектов. Не использовать ранее загруженный объект после ожидания блокировки. Ошибка до commit полностью откатывает удаление; после commit потерянный ответ восстанавливается идемпотентным replay DELETE. Прежние operation keys не могут воссоздать удалённый тест. Media чистится после commit только при отсутствии ссылок других тестов; сбой очистки оставляет недоступный мусор, а не битые чужие изображения. Сохранённый на диске backup удалением не переписывается, его срок хранения определяется общей политикой резервирования.

## 5. Публикация

1. PUT черновика содержит expected_revision. Неполные учебные поля допустимы, неверные типы/чрезмерные объёмы — нет.
2. Publish проверяет название, время, квоту, вопросы, опции, эталоны и принадлежность media. Предлагаемые пределы: 1–200 вопросов, 2–30 вариантов, 1–50 допустимых строк, 1–1440 минут, до 1000 попыток либо unlimited; условие/ответ до 20 000 символов, опция до 2000. Пределы требуют согласования.
3. Одна транзакция создаёт версию и переключает current_version_id/публикацию. Конфликт revision → 409. Повтор ключа → тот же version_id.
4. Медиа заранее проверено и находится в неизменяемом хранилище. Неуспешная публикация может оставить только неиспользуемый файл для уборки, но не битую ссылку в опубликованном тесте.
5. Старые попытки читают только свою version_id, включая эталоны и изображения. Не искать эталон по позиции в новом черновике.
6. Копия — новый test_id и непубликованный черновик. История, grants и использованные попытки не копируются. Общие неизменяемые media можно переиспользовать по ссылкам.
7. Ручной порядок тестов меняется транзакционно, с общей ревизией каталога и проверкой состава ID. Два администратора не перетирают порядок молча.

## 6. Жизненный цикл попытки

### 6.1 Начало и квота

Просмотр каталога/модалки попытку не создаёт. Только POST start расходует квоту. В BEGIN IMMEDIATE: повтор ключа → прежняя попытка; существующая active → вернуть её; иначе проверить публикацию, доступ, лимит, назначить attempt_no, серверное время, deadline_at и строки ответов; commit.

Перед веткой существующей active проверить дедлайн: просроченную финализировать, затем заново оценить возможность старта. Replay старого start_request_key всегда возвращает именно прежнюю попытку, даже завершённую; для действительно новой нужен новый ключ.

Предложение: все начатые попытки test_id во всех версиях расходуют квоту, включая pending и timeout. Доступно = max(0, текущий опубликованный attempt_limit + сумма grants − число начатых попыток). NULL = unlimited. Изменение лимита влияет только на новые старты; active не отменяется. Grants не исчезают при переключении режима. Правило требует подтверждения.

Двойной клик, два устройства и повтор после сетевого timeout не создают две попытки. Защита — UNIQUE и транзакция, а не только отключённая кнопка.

### 6.2 Один пишущий клиент

Авторизация — существующая Flask-сессия. Дополнительно попытка имеет generation и случайный токен владения; сервер хранит только его хэш. Для каждого загруженного документа создаётся новый writer_client_id, а токен хранится только в памяти этого документа, не в URL, localStorage или sessionStorage: браузер может копировать sessionStorage при дублировании вкладки. Новая вкладка/устройство получает read-only состояние и явное действие «Продолжить на этом устройстве». Перезагрузка не теряет сохранённые ответы и дедлайн, но требует нового claim через то же действие. Эта деталь активации подлежит согласованию вместе с переносом устройства; нельзя обещать единственного writer только на основании sessionStorage.

POST claim с expected_generation атомарно увеличивает generation и выдаёт новый токен. Старое устройство получает 409 SESSION_REPLACED, прекращает запись и сообщает о переносе. Heartbeat не захватывает попытку заново. При двух одновременных claim один проходит, второй получает conflict.

Каждая запись проверяет session.user_id, токен и generation; токен не заменяет CSRF. Администратор не меняет ответы. Потерянный ответ claim: клиент получает актуальную generation и делает новый явный claim, сервер не хранит секрет в открытом виде для replay. На новом устройстве продолжается прежний дедлайн; выход/потеря сети не останавливают время.

### 6.3 Автосохранение

- Single: option_id/null; multiple: массив уникальных option_id; free: буквальная строка. Чужие ID, дубли, неверные типы и превышения → 422.
- Debounce ориентировочно 500–800 мс, flush при смене вопроса, blur и завершении. Выбор можно сохранять сразу. Интервал уточнить нагрузочной проверкой.
- PUT передаёт expected_revision, generation, mutation_id. Сервер проверяет владельца, состояние и дедлайн внутри короткой транзакции, затем CAS-обновление revision. Очистка ответа также сохраняется.
- Один последовательный запрос на вопрос; повтор mutation_id не увеличивает revision. Устаревший ответ сети не перезаписывает свежий текст UI.
- 409 ANSWER_CONFLICT возвращает владельцу текущие revision/ответ. Не применять слепое last-write-wins; сохранить несохранённый ввод в памяти, получить состояние и разрешить конфликт явно.
- Показывать «Сохраняется/Сохранено/Нет связи». При закрытии с несохранённым вводом — предупреждение. Гарантированный offline-режим не входит в задачу; sendBeacon не гарантирует доставку.
- Retry с ограниченным backoff и прежним ключом разрешён до дедлайна. После дедлайна поздний ввод не принимается независимо от клиентской метки времени.
- Submit может включать последний пакет ответов с revisions. До дедлайна пакет и завершение атомарны; конфликт → 409 без частичной записи. После дедлайна пакет игнорируется, финализируется только ранее сохранённое.

### 6.4 Серверное время и timeout

Внутри БД время хранится в миллисекундах: deadline_at = started_at + 1000 × time_limit_seconds версии. API отдаёт server_now/deadline_at в ISO 8601 UTC и remaining_seconds = max(0, ceil((deadline_at − server_now)/1000)). Браузер считает отображение от server_now и монотонного локального счётчика, периодически сверяясь; смена часов устройства не продлевает время.

Мутация получает серверное now после захвата write-lock. Если now >= deadline_at, запись отвергается и вызывается единая финализация. При равенстве время уже истекло. Задержанный блокировкой запрос не получает льготу по клиентскому timestamp.

Обязательны оба механизма:

1. Независимый `scripts/expire_test_attempts.py`, worker либо cron, не Flask threading.Timer. Короткими идемпотентными транзакциями закрывает expired active. Предложение: 5–15 секунд при постоянном worker либо минутный cron на ограниченном хостинге; допустимую задержку согласовать.
2. Проверка дедлайна при attempt/catalog/result/admin-запросах и записи. GET может инициировать системную финализацию просроченного состояния, но не принимать ответы. Это страховка после простоя, а не замена worker.

Граница приёма всегда deadline_at, независимо от задержки фонового процесса. Timeout: submitted_at = deadline_at, finalized_at = фактическое время обработки. Ручной submit: submitted_at = серверное now. elapsed_ms = min(max(submitted_at − started_at,0),1000 × time_limit_seconds_snapshot); elapsed_seconds = floor(elapsed_ms/1000). Остаток после завершения считается от submitted_at, а не от нового now, и фиксируется; при timeout равен 0.

Единый finalize: active → фиксация ответов → автооценки/пропуски → pending_review или graded → result_revision → commit. Два submit/worker/старое устройство не создают второй результат. Replay возвращает существующий результат. До завершения оценки не раскрываются.

Сбой до commit откатывает изменения, следующая обработка повторяет операцию. После commit и потери HTTP-ответа replay возвращает тот же результат. После перезапуска worker подбирает просроченные попытки; время не сбрасывается.

## 7. Проверка и результаты

### 7.1 Проверка

Single сравнивает ID, multiple — множества. Свободный ввод сравнивается буквально с каждой разрешённой строкой. Строка «0» не пустая. Для textarea предложен единый транспорт LF у автора и ученика; CRLF не нормализуется молча в функции проверки. Newline-контракт требует подтверждения.

Пропуск: null, [] или строка длины 0 соответственно типу. Пробельная строка не пустая. Предложение: пропуск сразу получает 0, даже manual, и не задерживает финал; was_unanswered фиксируется отдельно. Это пограничное правило согласовать.

Manual nonempty получает NULL. Админ выставляет 0/1, может изменить ручную и автоматическую оценку. Запрос содержит grade_revision/request_key; транзакция пишет old/new, администратора и время. Исходный ответ и auto_score сохраняются. Для пропуска предложено разрешить override: при 1 статус «Правильно», но ответ по-прежнему «Ответ не дан»; подтвердить отдельно.

Выставление оценки разрешено только для отправленных pending_review/graded. Active не оценивается администратором через этот интерфейс. Административный read может показывать служебное состояние, но кнопки проверки до отправки недоступны. Результат active для ученика возвращает 409 ATTEMPT_ACTIVE с переходом к прохождению, а не предварительные текущие оценки.

В review сохранить кнопку «Следующий непроверенный»: переход к следующему score=NULL по порядку версии с обходом от конца к началу; если NULL нет — кнопка недоступна. Для single показать выбранный и правильный текст; для multiple — все выбранные и полный эталонный набор; для auto free — буквальный ответ и все допустимые строки. Два равных блока на компьютере и вертикальные блоки на мобильном; manual без эталона остаётся одним блоком.

Два преподавателя: устаревшая grade_revision → 409. Нет массовой переоценки, комментариев, уведомлений и пятибалльных оценок. Последний NULL переводит попытку в graded. Последующая коррекция увеличивает result_revision и пересчитывает лучшую попытку.

### 7.2 Итоги

K — число score!=NULL, N — количество вопросов версии, S — сумма баллов, P=N−K. Пропуски с нулём входят в K.

- P>0: «Предварительно S из K проверенных», P ожидают; final_score и percentage в DTO = null. Не показывать окончательное S/N и процент.
- P=0: S/N и 100*S/N. В русской локали до одного десятичного знака. Хранить целые S,N, не округлённый процент.
- Лучшая попытка — максимум дроби S/N среди graded всех версий test_id. Сравнивать перекрёстным умножением. При равенстве предложено выбирать более позднюю submitted_at, затем больший id. Баллы/знаменатель принадлежат выбранной попытке.
- Нет graded → лучший результат «—», несмотря на предварительные баллы.
- Приоритет статуса каталога: active → «В процессе»; иначе последняя pending → «Ожидает проверки»; иначе есть graded → «Пройден»; иначе «Не начат». Старый лучший результат может показываться рядом с новой pending.
- Повторное открытие подробного результата — только для последней попытки конкретного теста, из каталога; без дополнительной кнопки в result. Преподаватель видит полную историю. Собственность старой попытки сама по себе не даёт ученику права на её подробности. После скрытия доступ к разрешённому последнему результату сохраняется, после удаления теста — нет.

Последняя определяется максимальным attempt_no среди всех начатых попыток этого user_id/test_id, включая active. Если последняя active, открывается прохождение, а предыдущий результат уже недоступен; после отправки доступны подробности новой последней. Это буквальное определение «последней попытки», единое для каталога и API. Лучшие S/N и процент могут относиться к старой попытке, но карточка не содержит разрешающей ссылки на её подробности. Проверка latest выполняется сервером в одном согласованном чтении на HTML/result API/GET attempt/выдаче связанных медиа и replay, а не только скрытием ссылок. Для принадлежащей ученику, но не последней попытки — 403 RESULT_NOT_LATEST; для чужой — 404. Открытая старая страница при следующем запросе/возврате в foreground закрывает доступ и предлагает перейти к актуальной; Cache-Control no-store не позволяет считать кэш разрешением. Уже прочитанные данные физически отозвать из памяти пользователя невозможно, но новые запросы старых подробностей запрещены.

### 7.3 Эталоны

Предложение: show_correct_answers_snapshot фиксируется при старте. Новое значение в черновике не меняет прежние результаты задним числом; политику подтвердить.

Утверждено: ученический DTO включает эталоны только для разрешённой последней попытки при state=graded, отсутствии любых score=NULL и show_correct_answers_snapshot=true. Пока остаётся хотя бы один непроверенный вопрос, скрыты все эталоны, включая автоматически проверенные вопросы. Собственные ответы, текущие статусы и предварительная сводка остаются видимыми. При pending можно сообщить о доступности после полной проверки только если показ включён и эталон предусмотрен. Без эталона ничего не обещать. При false эталонов и обещаний нет в HTML/JSON. Админ видит существующие эталоны нужной версии всегда; его доступ не ограничен последней попыткой.

## 8. Маршруты и API

Учитывать имена новых Blueprint в `app.py::check_auth`. JSON без сессии получает 401, а не HTML редиректа. Страницы используют безопасный login next. POST/PUT/PATCH/DELETE — CSRF, Content-Type, проверка структуры; GET не создаёт попытку и не изменяет публикацию.

По базовому согласованному объёму опубликованный каталог доступен всем существующим авторизованным ученикам; отдельные назначения группам/ученикам не добавляются. Администратор имеет полный административный доступ. Ученик читает только свою последнюю attempts/result по правилам 7.2; актуальность аккаунта и роль проверяются по users, а не только по cookie. Скрытый тест недоступен для нового старта, но последняя active продолжается. Все пути выдачи версии/ответов/медиа проверяют latest; старую версию нельзя получить обходным GET. Чужая попытка возвращает 404, собственная не последняя — 403. Гость получает login/401. ID в маршрутах — положительные integer с явными Flask-конвертерами, поэтому /new, /order и /review-queue не конфликтуют с /<id>.

### 8.1 Ученик

| Метод/путь | Назначение |
|---|---|
| `GET /tests` | Каталог |
| `GET /tests/attempts/<id>` | Прохождение либо переход на готовый результат |
| `GET /tests/attempts/<id>/result` | Только собственная последняя попытка; active ведёт к прохождению |
| `GET /api/tests` | Статусы, квоты, last_attempt_id, best; без эталонов |
| `GET /api/tests/<id>` | Модальное окно и доступность старта |
| `POST /api/tests/<id>/attempts` | Идемпотентный старт с request_key |
| `GET /api/tests/attempts/<id>` | Вопросы версии без эталонов, собственные ответы, revisions, время |
| `POST /api/tests/attempts/<id>/claim` | Право записи/явная смена устройства с expected_generation |
| `POST /api/tests/attempts/<id>/heartbeat` | Проверка дедлайна и владения без продления |
| `PUT /api/tests/attempts/<id>/answers/<question_id>` | CAS-автосохранение |
| `POST /api/tests/attempts/<id>/submit` | Финализация с опциональным последним пакетом |
| `GET /api/tests/attempts/<id>/result` | Проверка owner/latest; все эталоны скрыты до полной проверки |
| `GET /tests/attempts/<id>/media/<media_id>` | Медиа только своей последней попытки и её версии |

question_id — ID вопроса версии, не экранный номер. Персональные HTML/JSON: Cache-Control private,no-store. Не помещать в общий CDN-кэш. Медиа имеет отдельную проверку доступа, private-кэширование; наличие ID не даёт доступ ко всем материалам.

Минимальные контракты:

- Start: request_key; ответ 201 для новой/200 для replay или продолжения, attempt_id, state, server_now, deadline_at, generation. user_id/version_id/time_limit клиент не задаёт.
- Save: answer, expected_revision, generation, mutation_id; writer token передаётся отдельным заголовком. Ответ: revision, saved_at, server_now, deadline_at, state; никаких score/is_correct.
- Submit: request_key, generation и опциональный массив ответов с expected_revision. Ответ: attempt_id, state, result_url; подробный результат запрашивается отдельно.
- Grade: score (строго integer 0/1), expected_grade_revision, request_key. Ответ: grade_revision, result_revision, pending_count и пересчитанная сводка.
- Grant: amount (положительный integer в согласованном пределе), request_key. Ответ: grant_id и новое remaining_attempts. Значение user_id берётся из проверенного маршрута, не произвольного тела.

Heartbeat — ориентировочно раз в 15 секунд и при возврате вкладки в foreground; ученический pending-result опрашивать не чаще одного раза в 15–30 секунд с остановкой в фоне. Это настраиваемые интервалы, не гарантии точности дедлайна. Приватный media endpoint не открывает черновик/старую попытку ученику. Административная выдача медиа использует отдельный guard; совпадение media_id с изображением другой версии не даёт доступа к её тексту или эталонам.

| `GET /api/admin/users/<user_id>/tests` | Статистика ученика |
| `GET /api/admin/users/<user_id>/tests/<test_id>/attempts` | История с пагинацией |
| `POST /api/admin/users/<user_id>/tests/<test_id>/grants` | Добавочные попытки amount/request_key |

`GET /admin/user/<user_id>` остаётся прежним адресом с пятью вкладками. Подробности попытки в статистике — модальное окно только для чтения. Административный DTO не используется в ученическом экране.

### 8.3 Ошибки и replay

Единый JSON: error.code, безопасное error.message, field_errors при валидации, request_id. Не возвращать traceback, SQL, файловые пути, секреты или чужие ответы.

| HTTP | Случай | Реакция |
|---|---|---|
| 400 | BAD_JSON, CSRF_FAILED | Исправить запрос; при истёкшем CSRF безопасно получить новый и повторить с прежним ключом |
| 401 | AUTH_REQUIRED | Вход; таймер идёт; несохранённый ввод пока остаётся в памяти вкладки |
| 403 | ADMIN_REQUIRED, TEST_HIDDEN, RESULT_NOT_LATEST | Запрет роли/нового старта/старых подробностей |
| 404 | NOT_FOUND | Несуществующая/чужая попытка, без раскрытия её наличия |
| 409 | LIMIT_REACHED, ANSWER_CONFLICT, SESSION_REPLACED, REVISION_CONFLICT, ATTEMPT_CLOSED, ATTEMPT_ACTIVE | Обновить состояние, не повторять вслепую |
| 409 | DEADLINE_REACHED | Закрыть ввод, показать результат финализации |
| 413/415/422 | Размер/формат/семантика | Ничего не записать, показать ошибку |
| 429 | RATE_LIMITED | Retry-After без срыва штатного автосохранения |
| 503 | DB_BUSY/TEMPORARILY_UNAVAILABLE | Ограниченный retry с прежним ключом |
| 500 | INTERNAL_ERROR | request_id и откат транзакции |

Один ключ с другим payload → 409 IDEMPOTENCY_KEY_REUSED. Replay снова проверяет права. Ключи нельзя удалять раньше допустимого окна повторов; для start/grant/grade уникальность хранится с доменной записью. Claim имеет особую процедуру восстановления без сохранения открытого токена, описанную выше.

Проверку дедлайна и commit timeout выполнить до формирования ошибки DEADLINE_REACHED; исключение обработки HTTP-ошибки не должно откатить финализацию. Запрос без прав не получает результат; worker всё равно завершит попытку самостоятельно. Replay прежнего save/submit после смены writer не применяет старый payload и не возвращает владение. Удалённый ресурс не воссоздаётся при replay: сохранённая запись операции возвращает 404/закрытое состояние. Срок хранения ключей должен учитывать этот случай.

## 9. Безопасность и эксплуатация

Основание — текущий код и `DEVELOPMENT_LOG.md`; историческая отметка «исправлено» не заменяет актуальную проверку.

| Наблюдение | Что включить в реализацию |
|---|---|
| Есть CSRF, параметризованный SQL, whitelist replace_markers, POST logout, safe next | Сохранить и покрыть регрессиями HTML/JSON/FormData, XSS и авторизации |
| init_db() при импорте, print с паролем создаваемого администратора | Отделить bootstrap, убрать вывод пароля до новых служебных команд |
| get_db() не включает foreign_keys | Проверить сироты на копии, согласовать очистку, затем единый factory |
| delete_user пропускает некоторые progress/last_answer | Исправить и проверить до включения FK |
| save_results/finish_exam повторяемы, время клиентское | Не копировать в тесты; старое укрепление — отдельная согласованная работа |
| exam/reshenie передают полный tasks | Отдельный сериализатор без эталонов в тестах; исправление старого экзамена отдельно согласовать |
| Конструктор теории интерполирует поля в innerHTML/value | Использовать textContent/DOM API; тестировать кавычки и теги |
| save_theory_api сравнивает удаляемые пути с images из входного JSON | Это не доверенный реестр: проверять сохранённый JSON и canonical path; аналогично урокам |
| Проверка расширения/magic bytes не равна декодированию | Проверять реальные PNG/JPEG/GIF, размеры, объём; не принимать пользовательский SVG/HTML |
| visualizer исполняет код через exec в процессе | Не использовать для тестов/подсветки; отдельный риск изоляции и ресурсов, не доказательство конкретного обхода |
| Нет явной полной конфигурации cookie security в app.py | Проверить реальное HTTPS, Secure/HttpOnly/SameSite, production WSGI и debug без вывода секретов |

Медиа хранить в private `data/tests/media/`, вне static; UUID-имя, авторизованная выдача. Проверять декодирование, MIME, размеры и общий текущий лимит multipart 5 МБ. Возможная библиотека декодирования требует отдельного согласования; сейчас зависимости не устанавливаются. Последовательность staging → проверка → неизменяемый файл → ссылка БД; старое изображение не удаляется при правке новой версии.

Не писать в обычные логи пароли, cookie, writer token, полные ответы/персональные данные. Журнал оценок доступен администратору. Ограничения login/start/claim/grant/upload должны работать между процессами: reverse proxy и доменные лимиты БД, не Python-словарь одного worker. Инфраструктуру подтвердить.

SQLite: короткие BEGIN IMMEDIATE, ограниченный busy_timeout, один commit на событие, без декодирования изображений/сети под write-lock. WAL рассматривать только после проверки хостинга, файловой системы и backup. Нагрузку проверить конкурирующим autosave/worker. PostgreSQL в текущий объём не входит.

Контролировать active/pending, возраст очереди, лаг expired active, p95 autosave, SQLITE_BUSY и ошибки worker. Работоспособный фоновый запуск — условие открытия старта ученикам.

Разделить флаги: доступность каталога, разрешение новых стартов, административные записи и обслуживание прежних attempts/results. Скрытие каталога или запрет новых стартов не отключает autosave/submit/worker для active. Публикация и права проверяются на сервере независимо от скрытых кнопок. Периодическое резервирование после запуска проводится по согласованному расписанию; перед технической паузой новые старты запрещаются и по возможности дожидаются окончания active, иначе применяется заранее согласованная процедура сбоя.

## 10. Приёмочные сценарии

Все серверные проверки — на временной SQLite и фиктивных пользователях, с управляемыми часами. E2E — Chrome, без рабочей БД.

| ID | Ожидаемый результат |
|---|---|
| T01 | Single: правильный ID=1, другой=0, чужой ID отклонён |
| T02 | Multiple: точный набор независимо от порядка=1; недобор/лишний=0; дубли/чужие ID=422 |
| T03 | Free: все допустимые строки проходят; регистр/пробелы/переносы значимы; строка «0» не пропуск |
| T04 | Manual nonempty=NULL, пустой=0; score=2 или true запрещён |
| T05 | 8 вопросов: предварительно 3/6 и 2 pending без итогового процента; после проверки 5/8=62,5% |
| T06 | Коррекция auto 0→1→0 пересчитывает итог/лучший, исходный ответ и auto_score прежние |
| T07 | Старые 3/4=75% выше новых 5/8=62,5%; pending исключён, tie-break стабилен |
| T08 | Публикация v2 при active v1 не меняет условия, эталоны, медиа, время и политику v1 |

| T13 | Submit одновременно с autosave/worker: одна финализация без частичной записи пакета |
| T14 | Два преподавателя: stale grade_revision получает 409 |
| T15 | Пока есть NULL, все эталоны скрыты даже у проверенных вопросов; после полного graded появляются только при включённом показе; manual без эталона ничего не обещает |
| T16 | Гость/ученик/админ, чужие attempt/question/media/grant, CSRF/replay; старые собственные подробности запрещены всеми путями, admin видит все; после нового старта прежний result недоступен |
| T17 | XSS/SQL/path traversal/ложный MIME/размер/enum не исполняются и не повреждают файлы |

Дополнительно к T09/T12/T20 проверить replay start, который ранее вернул существующую active; commit timeout при HTTP 409; отсутствие повторного создания удалённого ресурса; неизменность alt/media старой версии. Значения 0/1 в T01 обозначают начисленные баллы, а не фиксированные ID вариантов ответа.

## 11. Решения для согласования

1. Область одной активной сессии: на тест (предложено) или глобально; явный takeover устройства/вкладки и повторная активация после перезагрузки без потери сохранённых данных.
2. Квоты по всем начатым попыткам и действие нового лимита; компенсация длительного сбоя через grant, без автоматического возврата по умолчанию.
3. Только привязка настройки показа к snapshot либо её ретроактивное изменение требует решения. Сам показ исключительно после полной проверки уже утверждён; раскрытие перед следующей попыткой является следствием этого правила, а не новым вопросом.
4. Пропущенный manual=0, override пропуска, tie-break равных процентов.
5. Worker/cron, частота, допустимый лаг и обслуживание при active. Без фонового механизма старт не открывать.
6. Сроки хранения и backup, операционное окно для крупных удалений. Уничтожение теста вместе с active/результатами после подтверждения уже утверждено и повторного выбора архивирования не требует.
7. Технические пределы и newline-контракт строгих строк.
8. Декодирование изображений и локальная подсветка: выбор библиотеки, закрепление версии/лицензии — отдельное решение, установки сейчас нет.
9. Предварительное закрытие подтверждённых рисков общего кода без полной переписи платформы.

Все перечисленные предложения не считаются уже согласованными. Дизайн семи прототипов утверждён, перепроектирование не требуется.
