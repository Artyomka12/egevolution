# Публикация v2.12.0 с сохранением серверных данных

Этот порядок относится к перенумерации старых №13 → №10, №23 → №13
при сохранении временной копии №23. Обычный git pull недостаточен.

1. Сохранить серверный `passenger_wsgi.py` вне каталога сайта. Заменить
   его временным WSGI, который возвращает только 503 и не импортирует app.
   Выполнить `touch tmp/restart.txt`, запросить сайт и проверить 503 и
   заголовок `X-EGEvolution-Maintenance: 1`. Убедиться, что прежние процессы
   приложения завершились и нет других писателей/фоновых заданий.
2. Создать свежую копию серверной `users.db` через SQLite backup API,
   проверить `PRAGMA integrity_check`, записать количества строк и скачать
   копию. Хранить вне webroot с приватными правами. Сохранить прежний SHA
   и убедиться, что отслеживаемые файлы сервера не изменены.
3. Установить проверенный релиз через `git pull --ff-only origin main`.
   Не копировать users.db, .local-data, .env или локальный WSGI на сервер.
   Не выполнять git clean. Страница технических работ остаётся активной.
4. Выполнить аудит (одна строка):

   ```bash
   python3 scripts/renumber_ege_tasks.py --source-ref 241d495a4ab41b761d4c1d36fc6dacb0a86c7068 --backup-dir ~/egevolution-backups
   ```

5. Если аудит прошёл, повторить эту команду с `--apply`. Скрипт создаёт
   ещё один бэкап БД и исходных JSON вне сайта. При обычной ошибке SQL
   откатывается, архив убирается, установленные материалы не изменяются.
   Повторный запуск при существующем архиве запрещён. При аварийном обрыве
   процесса оставить паузу и проверить БД/архив перед любыми действиями.
6. Сверить результаты, целостность, историю попыток, доступы и новый
   прогресс. Исторические баллы и ответы должны совпадать построчно;
   записи старого №10 удаляются из активного прогресса, №13/23 переносятся.
   Число строк прогресса поэтому не обязано оставаться прежним.
7. Вернуть сохранённый исходный WSGI, выполнить `touch tmp/restart.txt`.
   Проверить главную, вход, профиль, историю, задания 10/13/23 и теорию 8/14.

## Откат

Оставаться на технической паузе. Сначала определить, была ли миграция
закоммичена в БД. Для полного отката нужны вместе прежний код/контент,
согласованная резервная БД и прежнее состояние архива `.local-data`.
Не восстанавливать одну БД поверх нового контента и не копировать SQLite
файл при открытых соединениях/WAL. Сохранить неудачный результат отдельно.
Точные команды отката выбирать по фактической стадии, без git clean и
без удаления серверных .env, загрузок, Passenger-конфигурации или бэкапов.
После открытия сайта откат к старому бэкапу потеряет новые ответы — сначала
снова включить паузу и сохранить актуальные данные.
