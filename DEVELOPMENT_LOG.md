v1.10.1 — точечный патч сразу после v1.10.0, обнаружен пользователем по скриншоту живого сайта: страница списка тем теории (`/theory`) показывала тему №1 как «Закрыто» для залогиненных пользователей без явного разрешения администратора, хотя доступ к самой теме фактически уже открыт всем с v1.10.0. Причина — `theory()` для отображения бейджа дублировал сырой SQL-запрос к `user_theory_access` напрямую, в обход функции `check_theory_access()`, где было добавлено исключение для `task_num==1`; для гостей баг не проявлялся (эта ветка кода выполняется только при наличии сессии). Аналогичный список уроков (`preparation()`) этой проблемы не имел — уже и так вызывал `check_lesson_access()` напрямую, а не дублировал запрос. Исправлено заменой прямого запроса на вызов `check_theory_access()`.

Проверка заголовков ответа сервера выявила настоящую причину: `Cache-Control: max-age=3888000` (45 дней) и `Expires` на полтора месяца вперёд, без какого-либо параметра версии в URL файла. Если пользователь открывал `/stats` до сегодняшнего деплоя (когда на сервере лежал более старый `stats.css`), браузер продолжает использовать локально закэшированную старую копию до истечения 45 дней, не делая новый запрос к серверу вообще — классическая проблема устаревания статики без cache-busting. Та же конфигурация кэша обнаружена и на `design-system.css` — то есть проблема системная, а не специфична для одного файла, и будет повторяться на каждом будущем релизе для любой изменённой статики.

Исправление — добавлен параметр `?v={{ app_version }}` (переменная уже доступна во всех шаблонах с v1.10.0 через `@app.context_processor`) ко всем ссылкам на статические CSS/JS файлы: `base.html` (`design-system.css`, `scroll-reveal.js` — общие для всех 15+ страниц, наследующих `base.html`), и по одной ссылке в каждом из 13 отдельных шаблонов с собственным page-CSS (`stats.html`, `attempt_detail.html`, `choose_mode.html`, `profile.html`, `preparation_lesson.html`, `login.html`, `register.html`, `preparation.html`, `variant_list.html`, `tasks_list.html`, `teoria.html`, `tasks_view.html`, `teoria_zadanie.html`), плюс 5 ссылок в `visualizer.html` (`style.css` и 4 JS-файла). Итого 20 ссылок в 16 файлах. Favicon и пользовательские изображения (аватары, логотип) cache-busting не получили — не критично к устареванию, не подвержены проблеме на каждом релизе (эти файлы почти никогда не меняются). Теперь при каждом повышении `APP_VERSION` URL всех изменившихся файлов автоматически меняется, и браузер гарантированно скачивает свежую копию вместо использования устаревшего кэша.

### v1.7.2 — Диаграммы функций в Block Scheme + витрина на главной

**Дата:** 2026-07-01

**Описание:** Пользователь показал скриншот с рекурсивным `factorial` — Block Scheme рисовал `def factorial(n):` как обычный блок и полностью игнорировал тело функции. Реализована полноценная поддержка: отдельная диаграмма на каждую функцию с анимацией передачи аргументов и возврата значения. Заодно добавлена блок-витрина визуализатора на главной странице (по итогам предыдущего обсуждения "визитной карточки") и исправлены два обнаруженных в процессе бага.

**1. Диаграммы функций (`static/visualizer/js/block-scheme.js`):**

- Парсер: `def` больше не проваливается в общий `action`-блок и не пропускается вместе с телом — новый путь `parseFunctionDef()`, тело рекурсивно разбирается через `parseBlock()`, функции «всплывают» отдельным списком (`functions[]`), не попадая в основную последовательность
- Новый тип узла `return` — форма «перевёрнутая трапеция» (`drawTrap()`, уже сверху/шире снизу), собственный цвет `--bs-return-fill/stroke/text` (светлая и тёмная тема), тупиковый блок: ни `layoutCond()` (все три варианта — верхний уровень / в цикле не последний / в цикле последний), ни `addColArrows()` не рисуют исходящую стрелку от ветки, заканчивающейся на `return`
- `layoutProgram()` (заменил `layoutTree()`): главная диаграмма как раньше + диаграмма на каждую функцию, столбцом справа, друг под другом в порядке определения; у функций нет овала «Конец» — обрываются на последнем блоке
- Анимация: карта `scope_id → строка вызова` (`bsCallSiteLine`, строится один раз из полной трассировки при загрузке). При `call`-шаге аргументы летят по невидимой прямой от блока-вызова к «Начало (имя)»; при `return`-шаге значение летит обратно именно к тому блоку, откуда сделан этот конкретный вызов — работает одинаково для рекурсии (вызов из той же диаграммы, например `return n * factorial(n-1)` вызывает саму себя) и для вызова одной функции из другой
- **Проверено без браузера**: вся логика (парсер → layout → анимация) прогонялась через Node напрямую на реальных данных `tracer.py` (не моках) — факториал (рекурсия, 4 уровня вложенности), две функции, вызывающие друг друга (включая функцию без явного `return`), `bubble_sort` (вложенные циклы + условие + return, полная трассировка 59 шагов) — во всех случаях 0 промахов резолва call/return в нужные блоки

**2. Исправлен баг — источник шарика Memory/Output:**

- После `return`-события шарик к панелям «Переменные»/«Вывод» летел от блока самого `return` (в диаграмме функции), а не от блока, где функция была вызвана — обнаружено пользователем визуально, подтверждено на трассировке `tracer.py` (синтетический финальный шаг трассировки указывает на строку глубоко в рекурсии из-за особенности поиска в `tracer.py`, не трогали)
- Причина не специфична для этого edge-case — общая: `srcEl` в `bsStepNext()` брался из «последнего активного блока», а после цепочки `return` это всегда сам оператор `return`, а не место вызова
- Исправление переиспользует ту же карту `bsCallSiteLine`: если текущий шаг — `return`, источник шарика подменяется на call-site
- Раньше не проявлялось: до этой версии строки внутри `def` не были блоками вообще, `srcEl` был `null`, анимация тихо не запускалась — баг стал видимым именно после появления диаграмм функций
- Проверено сравнением до/после на одной и той же трассировке `factorial(5)`: шарик вывода "120" — было `fromLine:4` (диаграмма функции), стало `fromLine:6` (главная диаграмма, `print(factorial(5))`)

### v1.2.3 — Безопасный replace_markers (XSS-2)

**Дата:** 2026-06-15

#### XSS-2 (ВЫСОКИЙ): уязвимая ветка в replace_markers
- **Проблема:** `app.py`, строки 97–98 (было):
  ```python
  if "<sup>" in text or "<sub>" in text or "<b>" in text or "<i>" in text:
      return markupsafe.Markup(text)   # текст не экранировался
  ```
  Если строка содержала хотя бы один из четырёх разрешённых тегов (`<sup>`, `<sub>`,
  `<b>`, `<i>`), весь текст целиком помечался как доверенный HTML без экранирования.
  Любой другой тег в той же строке (`<script>`, `<img onerror=...>`, `<iframe>`)
  передавался браузеру как сырой HTML. Источник данных — task/theory JSON,
  редактируемый администратором.

- **Исправление:** Уязвимая ветка удалена. Обе старые ветки (сырые HTML-теги и
  BBCode-маркеры `[sup]` / `[sub]` / `[b]` / `[i]`) объединены в единый безопасный
  pipeline:
  1. Все вхождения обоих форматов (`<sup>`, `[sup]` и т.д.) заменяются на нейтральные
     плейсхолдеры `___SUP___` и т.п. — до экранирования.
  2. `str(markupsafe.escape(text))` экранирует весь оставшийся HTML (`<script>`,
     `<img>`, `onerror`, `<iframe>` и любые другие теги и атрибуты).
  3. Только плейсхолдеры из whitelist восстанавливаются в HTML-теги.
     `str()` перед `.replace()` обязателен: замена на объекте `Markup` автоматически
     экранировала бы HTML-строки при подстановке.
  - **Whitelist:** `sup`, `sub`, `b`, `i` (открывающие и закрывающие).
  - **Файл:** `app.py`, функция `replace_markers`

- **Проверка (12 тестов):**

| `x<sup>2</sup>` (task_15) | `x<sup>2</sup>` ✅ | `x<sup>2</sup>` ✅ |
| `<b>Пример</b>` (theory_26) | `<b>Пример</b>` ✅ | `<b>Пример</b>` ✅ |
| `<i>код</i>` (theory_26) | `<i>код</i>` ✅ | `<i>код</i>` ✅ |

### v1.2.7 — Исправление D-2 и D-3: валидация task_id и generic-ошибки

**Дата:** 2026-06-16

#### D-2: task_id из JSON не валидируется как int (LOW, целостность данных)

- **Проблема:** В `POST /api/variants/save` значение `task_id = ref.get("task_id")`
  бралось из тела запроса без проверки типа и передавалось прямо в INSERT.
  SQL-инъекция невозможна (`?`-плейсхолдер), но в `task_usage` могло попасть
  `None` (IntegrityError → partial failure), строка или float вместо int.
  Дополнительно: JSON-файл варианта писался на диск ДО INSERT в `task_usage`,
  поэтому при ошибке вариант оказывался создан, а `task_usage` — пустым
  (неатомарная операция, вариант существовал при 500 в ответе).

- **Исправление:** Добавлен предварительный цикл валидации `validated_tasks`
  **до** `os.makedirs()` и записи JSON-файла. Финальная реализация:
  ```python
  validated_tasks = {}
  for position, ref in tasks_refs.items():
      try:
          task_num_v = int(position)       # position — всегда строка (ключ JSON-объекта)
          task_id_raw = ref.get("task_id")
          if isinstance(task_id_raw, (bool, float)):
              raise TypeError              # bool/float — явно отклоняются до int()
          task_id_v = int(task_id_raw)    # int→int, "5"→5; None/list/dict→TypeError
      except (TypeError, ValueError):
          return jsonify({"error": f"Некорректный task_id в задании {position}"}), 400
      validated_tasks[position] = (task_num_v, task_id_v)
  ```
  В цикле INSERT используется `validated_tasks` вместо `tasks_refs`.
  - `bool` проверяется явно до `int()`: без проверки `int(True)` → 1 (тихая ошибка).
  - `float` проверяется явно до `int()`: без проверки `int(5.7)` → 5 (потеря данных).
  - Атомарность: при некорректных данных ни папка, ни JSON-файл не создаются.
  - Формат успешного ответа не изменился.

- **Файл:** `app.py`, строки 2015–2030 и 2062 (маршрут `/api/variants/save`)

- **Правила принятия/отклонения task_id:**
  - `int` (JSON `5`) → принимается
  - `str` с цифрами (JSON `"5"`) → принимается как `int` (совместимость)
  - `float` (JSON `5.7`, `5.0`) → **отклоняется 400** (явная проверка `isinstance`)
  - `bool` (JSON `true`/`false`) → **отклоняется 400** (явная проверка `isinstance`)
  - `null`, `"abc"`, `[]`, `{}` → **отклоняются 400**

- **Проверка (9 сценариев, изолированная БД):**

| Сценарий | HTTP | Папка на диске |
|---|---|---|

| `task_id: "5"` (str) | 200, принят как 5 | создана ✅ |
| `task_id: 5.7` (float) | 400 | не создана ✅ |
| `task_id: true` (bool) | 400 | не создана ✅ |
| `task_id: false` (bool) | 400 | не создана ✅ |
