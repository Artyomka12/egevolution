# CLAUDE.md — Руководство по проекту для Claude Code

## Описание и назначение

EGEvolution — учебная платформа для подготовки к ЕГЭ по информатике.
Сайт: egevolution.ru

Пользователи проходят варианты ЕГЭ, изучают теорию по заданиям 1–27,
решают практические задачи в уроках. Администратор управляет контентом
через встроенную панель.

**Текущая версия: v2.9.0** — два независимых улучшения за сессию: последний
проверенный ответ теперь сохраняется в поле ввода (уроки начальной подготовки
+ практика теории заданий) + защита от повторной отправки формы заявки
(`/register`). (1) Раньше ни `user_lesson_progress`, ни `user_theory_progress`
не хранили сам текст ответа — только счётчик попыток и флаг верно/неверно,
поэтому поле ввода после перезагрузки страницы всегда было пустым. По
прецеденту `user_variant_progress` (v2.6.0) добавлены две новые таблицы —
`user_lesson_last_answer`/`user_theory_last_answer` (`CREATE TABLE IF NOT
EXISTS`, существующие таблицы не тронуты) — хранящие ответ в виде JSON ровно
в той форме, в которой его уже собирает JS (строка / массив из двух строк /
массив массивов для табличного ответа). `check_lesson_task`/
`check_theory_answer` сохраняют ответ при **каждой** проверке независимо от
результата — по прямому решению пользователя это «последний проверенный»,
а не «последний верный» ответ: если последняя попытка была ошибочной, поле
после перезахода покажет именно её, а не пусто и не старый верный ответ.
`get_lesson_task_progress()`/`theory_task()` отдают `last_answer` вместе с
`attempts`/`is_correct`, JS-инициализация обоих шаблонов
(`preparation_lesson.html`/`teoria_zadanie.html`) распознаёт форму ответа по
структуре и подставляет значение в нужные `<input>`. Проверено сквозным
прогоном через `Flask test_client()` на всех трёх формах ответа, включая
сохранение именно неверного варианта; тестовые данные не оставлены в
продовой `users.db` (перед прогоном сделана резервная копия, после —
удалены только тестовые строки). (2) Пользователь сообщил: при медленном
интернете или перегруженном сервере отправка заявки шла долго, люди не
понимали этого и жали кнопку по нескольку раз — прилетали дубли заявок.
Найдена реальная причина задержки, не только её симптом: `register()`
раньше синхронно ждал ответ от Telegram Bot API внутри самого запроса
(`notify_new_application()`, `timeout=5` секунд) прежде чем отдать
пользователю редирект — вынесено в фоновый `threading.Thread(daemon=True)`,
ответ теперь уходит сразу после записи заявки в БД (проверено: ~7мс вместо
потенциальных секунд ожидания). Плюс кнопка «Отправить заявку» получила
`onsubmit`-обработчик — мгновенно блокируется (`disabled`) и меняет текст на
«Отправляем...», не давая повторным кликам во время ожидания навигации
браузера дойти до сервера. По решению пользователя серверная защита от
дублей (проверка «такая же заявка недавно уже была») сознательно не
добавлена — рассмотрена и отклонена как отдельный пункт. См.
`DEVELOPMENT_LOG.md` (v2.9.0) для подробностей.

v2.8.0 — блок-схема визуализатора: исправлена стрелка
`break` внутри вложенного цикла. Найдено пользователем на реальном коде сразу
после релиза v2.7.0 (`for i: for j: if j==5: break` / `print(i,j)`) — стрелка
резала диаграмму насквозь через условие и вложенный цикл вместо аккуратного
выхода к внешнему `for`. Причина — `resolveBreaks()` для случая «цель выше
точки break» (break во вложенном цикле → продолжение внешнего) с v2.3.0
использовала наивный поворот сразу на общую центральную колонку. Правка в
два захода: **первая версия** — обход по границе рамки своего (внутреннего)
цикла, тем же приёмом, что уже применяется для обычного выхода из вложенного
цикла; убрала прорезание диаграммы, но создала новую путаницу — линия шла
рядом с родной стрелкой возврата внешнего цикла, но не совпадала с ней
(пользователь: «стало вообще непонятно»). Пользователь сам предложил решение
— вести `break` прямо до той же боковой стрелки, что и родной возврат, дать
им слиться в одну линию. **Вторая версия** реализует это точно: геометрия
теперь резолвится лениво в `resolveBackArrows()` (когда рамки внешнего цикла
уже посчитаны) и ведёт ровно к той же границе и точке входа, что и родная
стрелка `nestedLoopBackArrow` — координаты хвоста обеих линий совпадают в
точности. Проверено строгим геометрическим чеком (ни одна линия не
пересекает чужую фигуру) на 6 сценариях break (в «Да»/«Нет»-ветке, тройная
вложенность, break последним без ветвления, break не во вложенном цикле —
старый путь, `for` внутри `while`) + 4 более ранних (рекурсия, мёртвый
if/else, comprehension) — 0 пересечений; полные старые наборы тестов
(15+7+12) — 0 падений. Изменения — только в `resolveBreaks()`/
`resolveBackArrows()` одного файла. Отдельно, вне очереди — обновлена
ссылка на MAX везде на сайте (5 вхождений) и убраны ссылки на «ВКонтакте»/
«VK Видео» из футера (решение пользователя). См. `DEVELOPMENT_LOG.md`
(v2.8.0) для подробностей.

v2.7.0 — визуализатор Python-кода: декомпозиция
comprehension в блок-схеме + подсветка «Начало»/«Конец» + обложка ссылки.
Сессия началась с детального разбора всех открытых пунктов визуализатора
(без изменений кода): 2 пункта из `TODO.md` оказались уже исправлены ранее
(`.add()` для `set` — v2.3.0, `itertools.count()` внутри `all()`/`any()` —
v2.4.0), документация просто не была обновлена — исправлено сейчас; «висящая
стрелка» при мёртвом if/else внутри цикла — прогнано 7 сценариев, багов не
найдено, статус понижен до «подтверждено исправлено» (v2.3.0 `reachable`
закрывает класс полностью); тернарник (`return X if C else Y`) — разобрано,
почему безопасная декомпозиция сложнее, чем у comprehension (трассировка не
различает взятую ветку без риска расхождения Python/JS-семантики), пользователь
решил отложить — встречается редко. По ходу разбора пользователь показал
**другой** реальный баг — диаграмма функции без `else` в конце тела рисует
стрелку в пустоту (`layoutSeq`); решение найдено (убрать 4 лишние строки), но
по просьбе пользователя не применялось в этой сессии, только зафиксировано.

**Основная реализация** (`static/visualizer/js/block-scheme.js`) — сложные
`print(..., [comprehension])`/`return any(...)`/`all(...)` на блок-схеме
декомпозируются в `loop(+condition)+action` вместо плоского блока, переиспользуя
существующие фигуры и раскладку. Две формы: bracket-comprehension (где угодно
в строке) и `any()`/`all()` без фильтра — ровно паттерн реальных заданий
№19-21 (`return any(f(s2, m-1, N) for s2 in moves(s))` из их теории). Scope v1
— один `for`, максимум один `if`; сложнее — по-прежнему плоский блок без
ошибок. Три функции поиска узла по строке (`bsFindNodeByLine`/
`bsSetActiveBlock`/`bsFindEdgePath`) унифицированы на общий 3-уровневый
приоритет (action/return → condition → loop), т.к. несколько синтетических
узлов теперь могут делить один номер строки. В процессе тестирования на
реальном коде задания 19-21 найдены и исправлены 2 бага (потеря early-return
в ветке `all()`, `return [comprehension]` не декомпозировался вовсе).
Проверено 15 вариаций форм + 7 регрессий на обычном коде — 0 падений.

**Вторая фича** (тот же файл) — овалы «Начало»/«Конец» получили метку
`role: 'start'/'end'` (раньше не участвовали в анимации вовсе — у них нет
своей строки кода). Теперь запуск подсвечивает «Начало», и первый клик
«дальше» пускает шарик от него к первому реальному блоку; симметрично на
последнем шаге — шарик долетает до «Конец» и подсвечивает сам овал (раньше
работа тихо обрывалась на последнем действии). Работает и в обратную
навигацию. Проверено на примере с функцией и без — оба проходят полный
проход вперёд/назад без ошибок.

**Внеочередное** — обложка ссылки (`og:image` в `base.html`/`start.html`)
показывала устаревший скриншот старой видео-секции главной; заменена на

итогам уточняющего диалога: (1) убрана кнопка «🔄 Сброс» таймера и функция
`resetTimer()` — единственная кнопка блока таймера теперь «Завершить»; (2)
проверенные ответы (только через «Проверить» — вписанный, но не проверенный
текст сознательно не сохраняется) и оставшееся время таймера теперь
сохраняются на сервере, привязаны к `user_id`, а не к браузеру — переживают
не только обновление страницы, но и смену устройства, по прямому решению
пользователя (localStorage-only вариант обсуждался и отклонён); (3) заодно
исправлен сопутствующий баг — `ege_timer_variant_<n>` в `localStorage` раньше
не очищался никогда, из-за чего повторное решение того же варианта
продолжало отсчёт с прошлого места вместо 03:55:00. Реализовано через новую
таблицу `user_variant_progress` (`user_id`, `variant_num`, `answers_json`,
`time_remaining`, `UNIQUE(user_id, variant_num)`) — черновик текущей попытки,
полностью отдельно от `user_results`/`user_task_answers`: ничего не попадает
в статистику до нажатия «Завершить» (создание новой таблицы — пункт из
списка ниже, требующий явного подтверждения, — согласовано отдельно). Два
новых маршрута `GET/POST /api/variant_progress/<variant_num>` (auth-guard,
CSRF по стандартному для проекта `X-CSRFToken`-паттерну, upsert через
`ON CONFLICT`); синхронизация времени с сервером — по выбору пользователя
только вместе с каждой проверкой ответа, не отдельным периодическим тикером
(осознанный компромисс по точности при долгих паузах между проверками).
`/save_results` при успехе дополнительно удаляет черновик из
`user_variant_progress`. В `reshenie.html` таймер и восстановление ответов
теперь читаются через `GET /api/variant_progress/...` при загрузке страницы
вместо `localStorage`; общая функция `applyCheckResult()` переиспользуется
и для свежего ответа с `/check`, и для восстановления сохранённого прогресса.
`exam.html` не тронут — вне scope, как и раньше; существующие одноразовые
ключи `localStorage` (`variant_<n>_answers`/`variant_<n>_time`, которые сразу
после завершения читает `results.html`) не затронуты. Проверено
`Flask test_client()` (создание/восстановление/очистка черновика) и лично
пользователем вживую. Побочно, при самопроверке наполнения уроков по просьбе
пользователя, найден недоделанный черновик практики урока №9 «Визуализатор
Python» (1 задача с пустым описанием вместо обычных 11–20) — требует
уточнения с пользователем, не исправлялся в этой сессии.
См. `DEVELOPMENT_LOG.md` (v2.6.0) для более подробного описания.

**Block Scheme — диаграммы функций (v1.7.2):**

Изначально `block-scheme.js` строил только одну диаграмму и полностью игнорировал тела `def` (пропускались парсером). Теперь:

- Парсер (`parseBlock`/`parseFunctionDef`) распознаёт `def` отдельно от обычной последовательности — тело рекурсивно разбирается и «всплывает» через `functions[]`, а не остаётся в основном потоке; новый тип узла `return` (форма — перевёрнутая трапеция, свой цвет `--bs-return-*` в `style.css`, тупиковый блок без исходящей стрелки)
- `layoutProgram()` (заменил `layoutTree()`) строит главную диаграмму + отдельную диаграмму на каждую функцию, колонкой справа, друг под другом в порядке определения; диаграммы функций не имеют овала «Конец» — обрываются на последнем блоке
- Позиционирование колонки функций — не фиксированным отступом, а измерением: пробный проход `layoutSeq` при `cx=0` для каждой функции (`leftExtent()`), чтобы узнать её реальную левую границу с учётом вложенности циклов/условий, и только потом разместить с гарантированным зазором (`BS.FUNC_GAP_X`). Фиксированный отступ раньше приводил к наложению диаграмм при глубокой вложенности (обнаружено и исправлено в v1.7.2)
- Анимация вызова/возврата: карта `scope_id → строка вызова` (`bsCallSiteLine`, строится один раз из полной трассировки) — при `call`-шаге аргументы летят по невидимой прямой от блока-вызова к «Начало (имя)» нужной диаграммы; при `return`-шаге значение летит обратно именно к тому блоку, откуда был сделан этот конкретный вызов. Работает одинаково для рекурсии (вызов из той же диаграммы) и вызова одной функции из другой
- Источник шарика Memory/Output (`srcEl` в `bsStepNext()`) переопределяется на call-site по той же карте, когда текущий шаг — `return`: иначе шарик летел от строки самого `return`, а не от блока, где функция была вызвана (баг, найденный после того, как диаграммы функций стали реально рисоваться — раньше просто молчаливо не анимировался)
- `#bs-svg` — адаптивный (`max-width:100%; height:auto; min-width:650px`), сжимается под контейнер через свой `viewBox`; ниже `min-width` включается скролл (`#bs-canvas { overflow:auto }`) вместо дальнейшего сжатия

**Расширение whitelist (v2.1.0):**

Согласован и реализован пятипунктовый список новых конструкций (пункт про `turtle` отменён пользователем в процессе планирования — большой объём работы, реальной потребности в разборе задания №6 через визуализатор нет):

- **`import re`/`import itertools`** (и `from ... import ...`, алиасы) — настоящий импорт этих двух модулей выполняется по-настоящему; `math` сознательно не включён. Технический нюанс: `namespace['__builtins__']` в `tracer.py` пуст, поэтому `import` без кастомного `__import__` падает с `ImportError: __import__ not found` — добавлен `_restricted_import()`, проверяющий имя модуля по whitelist. `re`-объекты (`Pattern`/`Match` из `compile()`/`finditer()`) — их методы (`group`/`groups`/`span`/`start`/`end`) добавлены в общий `ALLOWED_METHODS` (нет отдельного механизма «доверенный модуль» — тот же плоский список, что и для `list`/`str`/`dict`). В блок-схеме `import`-строки рендерятся отдельным типом блока «предопределённый процесс» (прямоугольник с двумя вертикальными чертами по краям, `bs-import` в `block-scheme.js`/`style.css`) — определяется автоматически построчным парсером блок-схемы (`s.startsWith('import ')`), без AST.
- **`sys.setrecursionlimit()`** — не настоящий модуль `sys`, а `_FakeSys` в `tracer.py` с единственным методом; строка `import sys` разрешена валидатором, но физически вырезается из текста кода перед компиляцией (`_strip_sys_import()`, заменяет строку на пустую — работает и без явного `import sys`, т.к. заглушка всегда в `SAFE_BUILTINS['sys']`). Потолок 10 000 (`SYS_RECURSION_LIMIT_CAP`) — эмпирически проверено на деве до 3 000 000 без падения процесса при активном `sys.settrace()` на Python 3.12, потолок выбран не из соображений безопасности, а чтобы не создавать иллюзию пользы большего значения при `MAX_STEPS=1500`. Реальный лимит процесса (общий на Flask-воркер) сохраняется/восстанавливается `try/finally` вокруг каждой трассировки.
- **`open()`** — новый блок реальной загрузки файла на странице визуализатора (`#file-input` в `visualizer.html`, `editor.js` читает через `FileReader`). Фейковый `open(любое_имя)` в `tracer.py` игнорирует имя и режим, возвращает `io.StringIO(содержимое)` от реально загруженного файла — без обращения к файловой системе. `with open(...)` по-прежнему запрещён (`ast.With` в `FORBIDDEN_MESSAGES`) — только линейный `f = open(...)`, как в теории задания №17.
- **`any()`/`all()` + `ast.GeneratorExp`** — генераторные выражения структурно совпадают с уже разрешённым `ListComp` (тот же `ast.comprehension`), новых лазеек не открывают.
- Побочно найден (не исправлен, вне scope плана) предсуществующий пробел: метод `.add()` для `set` отсутствует в `ALLOWED_METHODS` — `s.add(x)` из теории урока №6 не выполнится в визуализаторе.

**Block Scheme — однострочные операторы и корректность рёбер/подсветки (v2.2.0):**

Найдено пользователем на реальном коде (рекурсия с однострочными `if условие: return ...`) — три связанных, но самостоятельных бага в `static/visualizer/js/block-scheme.js`:

- **Однострочные `if/elif/else/for/while/def`** (`if x: return y`, тело на той же строке) искажали диаграмму: `parseCond`/`parseLoop` ожидали двоеточие строго в конце строки, поэтому весь текст «условие: тело» целиком попадал в подпись блока, а ветка «Да» оставалась пустой (тело не находилось на отдельной, более отступленной строке, как того ожидал парсер). Баг оказался общим для всех 5 составных операторов, не только `if` — подтверждено отдельным прогоном каждого. Исправлено препроцессором `expandInlineBodies()`/`findTopLevelColon()` в `parseCode()`: однострочная форма разворачивается в стандартную двухстрочную (заголовок + синтетическая строка тела с отступом +4) ещё до основного разбора — сам парсер не менялся. `findTopLevelColon()` корректно пропускает `:` внутри строк, срезов (`A[1:2]`), словарей (`{1:2}`) и аннотаций параметров (`def f(x: int):`), считая, помимо кавычек, глубину скобок `()[]{}`. Обе синтетические строки помечаются **тем же номером исходной строки** — Python выполняет условие и тело такой строки как одно `line`-событие трассировки. Тернарник в `return` (`return X if C else Y`) сознательно не разворачивается — отдельный, более сложный случай (не начинается с ключевого слова, значит препроцессор его не трогает).
- **Пропадающая стрелка «Нет» у последнего условия функции** — диаграммы функций не имеют овала «Конец» (см. выше); если функция заканчивается голым `if` без `else`, точка `joinY` в `layoutSeq()` довязывается только при обработке следующего узла в последовательности — а следующего узла нет. Исправлено: после основного цикла `layoutSeq()` при незакрытом `joinY` дорисовывается короткий отрезок со стрелкой, вместо того чтобы оставлять линию без наконечника. Баг существовал независимо от однострочных операторов — воспроизведён и на чисто многострочном коде той же структуры.
- **Шарик анимации летел от блока условия, а не от `return`** — прямое следствие однострочных операторов: условие и его тело делят номер строки, а поиск узла по строке (`bsFindNodeByLine()`, `bsSetActiveBlock()`) брал первый попавшийся результат — всегда диаграмму условия, т.к. она кладётся в раскладку раньше своего тела. `bsFindNodeByLine()` (используется только в контексте `call`/`return`-переходов, где взятая ветка уже точно известна) теперь безусловно предпочитает не-`condition`/`loop` узел среди кандидатов с одинаковой строкой. `bsSetActiveBlock()` требует явного признака `isReturn` (`step.event === 'return'`, передаётся из `renderBlockSchemeStep()`) — на обычном `line`-шаге (условие могло не сработать) по-прежнему подсвечивается условие, и только на настоящем `return`-шаге подсветка переключается на блок возврата. `bsFindEdgePath()` (обычные переходы между соседними строками, не call/return) сознательно не тронут — там текущее поведение (предпочесть условие) уже правильное.

**Block Scheme — стрелка выхода из цикла, недостижимый join, break/continue (v2.3.0):**

Пользователь протестировал визуализатор вживую и последовательно прислал 9 находок; 7 — реальные баги, все исправлены в `static/visualizer/js/block-scheme.js`:

- **`from module import *` не находил разрешённые имена** — `validator.py`: AST даёт для wildcard-импорта только буквальный токен `'*'`, а не реальные имена модуля, поэтому `product(...)`/`combinations(...)`/`findall(...)` после `from itertools import *`/`from re import *` отклонялись как незнакомые. `RE_FUNCS`/`ITERTOOLS_FUNCS` вынесены в именованные наборы (раньше — просто часть плоского `ALLOWED_METHODS`); при `alias.name == '*'` в сборе `imported_names` подставляется весь набор соответствующего модуля.
- **`.add()` для `set`** — добавлен в `ALLOWED_METHODS` (пробел, найденный и отложенный ещё при v2.1.0).
- **`map`/`filter`** — отсутствовали в whitelist целиком, обычный недосмотр (не сознательное решение); добавлены в `ALLOWED_BUILTIN_CALLS`/`SAFE_BUILTINS`. Особенно заметно теперь, когда `open()` уже поддержан — `map(int, f.readline().split())` стандартная идиома чтения чисел из файла.
- **Нет стрелки «цикл → следующее условие»** — в `layoutSeq()`/`linSeq()` ветка обработки `condition` не проверяла `lastLoop` (в отличие от обычных узлов, где проверка была). Исправлено общим хелпером `loopExitArrow()`, вызываемым из всех трёх веток (`loop`/`condition`/обычный узел) в обеих функциях — заодно закрыт непроверенный, но тем же классом бага сломанный случай «цикл сразу за циклом». `placeLoop()` этой проблемы не имел — уже флашил `lastInnerLoop` безусловно в начале каждой итерации тела.
- **Дух-стрелка между диаграммами функций (регрессия v2.2.0)** — правка «закрыть висящий join» из v2.2.0 не проверяла, было ли что-то реально нарисовано в эту точку: если/else, где ОБЕ ветки заканчиваются `return` (как в реальном коде пользователя), ничего не подключает к `joinY`, но старая версия правки всё равно рисовала исходящую стрелку из пустоты. `layoutCond()` теперь возвращает `{y, reachable}` вместо голого числа во всех 5 точках `return` (включая условный `backArrow` к началу цикла в ветке «INSIDE LOOP, LAST» — там та же проблема была, просто не проявлялась в присланном примере); все 4 места, где закрывался «висящий» join (`layoutSeq`, `linSeq`, `placeLoop`×2, `mergeFrom`), теперь рисуют ребро только при `reachable: true`.
- **`break`/`continue` не имели выхода из цикла на диаграмме** — раньше падали в обычный `action`-блок безо всякой специальной обработки. `parseBlock()` распознаёт оба явно; `endsInReturn()` расширена на `break`/`continue` (тот же смысл — «дальше по этой ветке рисовать нечего», имя не переименовано ради размера диффа). `continue` переиспользует существующий `backArrow` к началу цикла. `break` — новый отложенный коннектор (`registerBreak()`/`resolveBreaks()`, `Map` по id цикла на уровне модуля, сбрасывается в `layoutProgram()`): break всегда ведёт туда же, куда вёл бы естественный (небрейкнутый) выход из объемлющего цикла, просто раньше — поэтому разрешается в реальное ребро именно в момент, когда становится известна точка естественного выхода самого этого цикла (единая логика для прямого выхода, вложенного цикла через `nestedLoopBackArrow`, и ветки `if`, заканчивающейся циклом, через `mergeFrom`). Если цикл с незакрытыми `break` сам оказался последним оператором функции — та же заглушка со стрелкой, что и для голого `if` без `else`. Отдельно найдено пользователем на реальном коде уже после первой версии этой правки: когда break регистрируется из ветки, чья колонка (`targetCx`) совпадает с колонкой самого условия/цикла — а так происходит в типичном случае `if k==5: break` последним оператором цикла — исходная геометрия `resolveBreaks()` (короткий спуск + ранний поворот на `targetCx`) заставляла линию break идти вдоль/сквозь «Нет»-стрелку этого же условия и обратную стрелку цикла на приличном участке, физически сливаясь с ними в нечитаемый пучок. Исправлено: `resolveBreaks()` держит вертикальный участок на исходной колонке ответвления break как можно дольше — вплоть до низа рамки цикла целиком (`loopNode.frameBot`) — и поворачивает на `targetCx` только у самой цели; полностью развести линии в этой геометрии невозможно (obратная стрелка цикла разворачивается на всю ширину рамки и неизбежно проходит через колонку break на пути вниз), но результат — одно короткое чёткое перпендикулярное пересечение вместо развёрнутого наложения, проверено визуально через headless-рендер SVG (Edge) на исходном примере пользователя и 4 регрессионных сценариях (одиночный break, break внутри вложенного цикла, break+continue вместе, break последним оператором функции, заканчивающейся циклом) — везде тот же паттерн: одно аккуратное пересечение вместо путаницы.
- **Серый шарик анимации долетал позже, чем стартовал следующий шаг** — длительность `bsAnimateFlowCursor()` растёт с длиной пути на экране (до `BS_FLOW_MAX_MS=1400мс`), но была помечена как «чисто декоративная, не блокирующая» и не входила в ожидание перед следующим шагом (`BS_SPEED_PAUSE=450мс` на обычной скорости) — на длинных стрелках это создавало заметный визуальный разнобой. Пользователь выбрал вариант A (полная синхронизация): `bsAnimateFlowCursor()` получила третий параметр `onComplete` (обязательно вызывается и в раннем `return` на вырожденном пути — иначе шаг завис бы навсегда); `bsStepNext()` собирает все её вызовы в `pending[]` и учитывает наравне с шариками переменных/консоли в общем `ballCount`/`onLand`.

**Трассировщик: общий лимит шагов на все типы событий, а не только `line` (v2.4.0):**

Найдено сразу после v2.3.0 по репорту пользователя «некоторые программы перестали запускаться» (3 приложенных примера, все реальные — не ошибка пользователя, в отличие от «Кода 1» из v2.3.0). Причина — архитектурный пробел в `tracer.py`, независимый от правок Block Scheme: `MAX_STEPS` ограничивал только `'line'`-события; ветки `'call'`/`'return'` дописывали шаг в `steps` безусловно, без какой-либо проверки лимита. Это было безобидно до v2.1.0 (разблокировка `any()`/`all()` + `ast.GeneratorExp`) — генераторное выражение создаёт собственный Python-фрейм, и каждое его вычисление внутри цикла даёт `call`/`return`-событие, полностью в обход `MAX_STEPS`. Замерено напрямую через `trace_code()`: пример пользователя с `combinations(...)` + `all(f(x) for x in ox)` — **198.6 сек, 81.6 млн шагов** (`line: 1000`, `call`/`return`: по ~40.8 млн); пример с `product(repeat=7)` — 41.4 сек, 14.6 млн шагов; изолированный синтетический повтор (`for i in range(200000): all(x>0 for x in [1,2,3])`) — 3.8 сек, 1.6 млн шагов, разбивка `{'line': 1000, 'call': 800000, 'return': 800000}` — `line` корректно упирается в лимит, `call`/`return` растут неограниченно.

Пользователь выбрал: общий счётчик на все типы событий (не отдельный бюджет для call/return) + компенсирующее повышение `MAX_STEPS` с 1000 до **1500**. Реализовано смещением проверки лимита в начало `tracer()` — до диспетчеризации по `event`, то есть `line`/`call`/`return` делят один и тот же `step_count`. Критическое отличие от старого поведения: при достижении лимита `tracer()` теперь **поднимает** `_StepLimitReached` (тихо перехватывается в `trace_code()`), а не просто прекращает запись — `sys.settrace()`-колбэк может прервать трассируемый код исключением, которое реально останавливает его выполнение (не только запись шагов), т.к. `try/except` запрещён валидатором и поймать это исключение в пользовательском коде невозможно (проверено отдельным изолированным тестом на raise из колбэка до внесения правки). Это не просто чинит утечку памяти/JSON-полезной нагрузки — реально обрывает зависшие миллионы итераций `for`/`product`/`combinations`, а не только останавливает их запись. Побочный эффект: строка `_StepLimitReached` реально прерывает выполнение и для документированного ограничения «`itertools.count()`/`cycle()` без `islice()` внутри `all()/any()` — бесконечный цикл» (см. ниже) — раньше это было настоящее зависание, теперь корректно обрывается на лимите (проверено: `all(x>=0 for x in itertools.count())` — 0.01 сек, 1500 шагов, `truncated=True`, вместо зависания).

Три захардкоженных упоминания «1000 шагов» в UI обновлены на «1500» (`templates/visualizer.html`, `static/visualizer/js/editor.js`, `static/visualizer/js/block-scheme.js`), по тому же паттерну, что и 600→1000 в v2.1.1. Проверено: все 3 примера пользователя — 0.01–0.02 сек вместо 41–198 сек, `truncated=True`, без ошибок; регрессия — простой код без обрезки (`truncated=False`), реальная ошибка пользователя (`ZeroDivisionError`) не путается с обрывом лимита, видимая глубина рекурсии с `sys.setrecursionlimit()` (~499 уровней при общем бюджете 1500 против прежних ~400–500 при бюджете 1000 только на `line` — сопоставимо, компенсация сработала как и предполагалось), `open()`/`re`/`itertools` — без регрессий; сквозной прогон через реальный `Flask test_client()`/`/api/visualizer/trace` на исходном примере пользователя.

**Известные ограничения (сознательно отложены):**

- Нет wall-clock timeout на трассировку как таковой (по реальным часам) — но с v2.4.0 общий лимит шагов (`line`+`call`+`return`) реально обрывает выполнение трассируемого кода, а не только его запись, что закрывает подавляющее большинство практических случаев зависания (циклы, genexpr, рекурсия). Не закрыт: одна физически тяжёлая строка/выражение, целиком выполняющаяся между двумя `line`-событиями без промежуточных вызовов (`2**10**8` и т.п.) — такая строка не создаёт ни одного трассируемого события до своего завершения, лимит проверить не на чем. Риск снижен закрытым доступом (только авторизованные), но не устранён
- Нет rate limiting на `/api/visualizer/trace`
- Block Scheme: возврат из функции с полностью «мёртвым» if/else внутри цикла (обе ветки — return) мог оставлять висящую стрелку — возможно устранено попутно правкой `reachable` в v2.3.0 (проверено эмпирически на синтетическом примере, падений/подозрительных рёбер не найдено), но отдельно как основной сценарий не тестировалось — не понижать до «исправлено» без прицельной проверки
- Block Scheme: тернарник в `return`/присваивании (`return X if C else Y`) не декомпозируется на ветвление — рисуется как единый текстовый блок, сознательно вне scope v2.2.0/v2.3.0
- Block Scheme: сложные `print(..., [comprehension])` рисуются одним плоским блоком, а не как настоящая структура цикл+условие+накопление — отмечено пользователем как идея на будущее, не баг, крупнее по объёму, чем точечная правка

## Архитектура контента

### Варианты (variants/)

Поддерживаются два формата JSON:

**Старый формат** — список полных объектов задач:
```json
[
  {
    "id": 1,
    "title": "Задание 1",
    "description": ["..."],
    "correct_answer": "42",
    "images": [{"path": "img.png", "after_paragraph": 0}]
  }
]
```

**Новый формат** — словарь ссылок на базу задач:
```json
{
  "1": {"task_id": 5},
  "2": {"task_id": 12}
}
```

Функция `load_variant_tasks(variant_num)` обрабатывает оба формата.
- Старый формат: задачи берутся из JSON варианта напрямую.
- Новый формат: задачи подтягиваются из `tasks/task_XX/tasks.json`.
  При загрузке устанавливается `task["id"] = task_num` и
  `task["_source_task_num"] = task_num` для корректной маршрутизации изображений.

### Маршрутизация изображений

- Новый формат: `url_for('task_images', task_num=task._source_task_num, filename=...)`
- Старый формат: `url_for('variant_images', variant_num=variant_num, filename=...)`

Проверка в шаблонах: `{% if task._source_task_num is defined %}`.

### База задач (tasks/)

`tasks/task_XX/tasks.json` — список объектов задач для задания №XX.
Используется конструктором вариантов и просмотром базы администратором.

### Теория (theory/)

`theory/task_XX/theory.json` — материал по заданию №XX:
- `theory.theory.description` — список абзацев
- `theory.theory.images` — изображения с привязкой к абзацам
- `theory.videos` — массив видео (новый формат)
- `theory.video` — одно видео (старый формат, обратная совместимость)
- `theory.practice.tasks` — практические задания

### Уроки (uroki/)

`uroki/urok_XX/urok_XX.json` — подготовительный урок (номер id встроен в имя файла,
в отличие от `theory/task_XX/theory.json`, где имя файла фиксировано, а номер лежит
внутри JSON как `task_id`). Формат (с v1.14.0, зеркально теории):
- `lesson_id` — номер урока, дублируется в самом JSON (зеркально `task_id`)
- `description` — короткое описание для карточки в каталоге `/preparation` (поля
  нет у теории)
- `theory.description` / `theory.images` — абзацы теории и картинки к ним
- `videos` — массив видео (`{path, title}`), несколько на урок — старый одиночный
  `video` поддерживается в шаблоне только для обратной совместимости
- `practice.tasks` — практические задания (заголовок, абзацы, картинки,
  прикреплённый файл в `uroki/urok_XX/practice_files/`, один из
  `correct_answer`/`answers`/`answer_grid`)

Доступ управляется через таблицу `user_lesson_access` (админ открывает/закрывает).

### Система сложности задач (DIFFICULTY_INFO)

Каждая задача в `tasks.json` может иметь поле `"difficulty"` с одним из четырёх значений:

| Ключ | Метка | Цвет |
|---|---|---|
| `easy` | Лёгкое | зелёный `#4ade80` |
| `medium` | Среднее | жёлтый `#facc15` |
| `hard` | Сложное | красный `#ef4444` |
| `grave` | Гроб | фиолетовый `#a855f7` |

Словарь `DIFFICULTY_INFO` в `app.py` содержит эти значения и используется
при отображении задач в базе и статистике. Если поле отсутствует — задача
считается `medium` по умолчанию.

## Деплой на продакшен (REG.RU)

Сайт egevolution.ru развёрнут на виртуальном хостинге REG.RU через Passenger.
GitHub — единственный источник актуального кода; на сервер файлы вручную
практически никогда не копируются (исключение — ручная загрузка больших
видеофайлов, которые не попадают в git из-за `.gitignore`).

**Рабочий каталог на сервере:** `~/www/egevolution.ru`
(полный путь: `/var/www/<логин>/data/www/egevolution.ru`) — это тот же
git-репозиторий, работа ведётся прямо в нём.

**Схема обновления:**

```
локальный ПК → git push origin main → GitHub (origin/main)
                                            ↓
                              SSH на сервер REG.RU
                              cd ~/www/egevolution.ru
                                            ↓
                              git pull origin main
                                            ↓
                              touch tmp/restart.txt
                                            ↓
                        Passenger отслеживает mtime этого файла
                        и сам перезапускает Flask-приложение
```

- `touch tmp/restart.txt` обязателен после любого изменения Python-кода,
  HTML-шаблонов, JS, CSS, а также `.env`. Если менялись только статические
  файлы (картинки, видео) — перезапуск обычно не нужен.
- `.env` существует **только на сервере**, в git не хранится. После правки
  `.env` на сервере тоже нужен `touch tmp/restart.txt`, чтобы Flask
  перечитал переменные окружения.
- Крупные видеофайлы (например, `static/videos/*.mp4`) исключены из git
  через `.gitignore` — их нужно заливать на сервер вручную отдельно от
  `git pull`.
- Никакие другие способы перезапуска (`systemctl restart`, `gunicorn`,
  Docker, CI/CD, Supervisor) в этой схеме не используются — переход на них
  не планируется без отдельного явного запроса.

## Правила работы Claude Code

### Обязательно перед изменениями
1. Прочитать файл полностью, найти все затронутые места.
2. Показать план изменений перед внесением.
3. Дождаться подтверждения пользователя.

### Запрещено без явного подтверждения
- Менять схему базы данных (`CREATE TABLE`, `ALTER TABLE`).
- Менять логику авторизации и проверки паролей.
- Менять формат хранения вариантов в JSON.
- Создавать новые таблицы в `users.db`.
- Менять `load_variant_tasks()` — критическая функция совместимости.
- Переименовывать маршруты (сломает закладки и внешние ссылки).
- Менять структуру директорий `variants/`, `tasks/`, `theory/`, `uroki/`.
- Добавлять зависимости в `requirements.txt` без согласования.
- Делать git push без явной просьбы пользователя.
- Изменять `.env` (содержит реальные секреты).

### Стиль кода
- Шаблоны: 16 пользовательских страниц наследуют `base.html`; `start.html`, `exam.html`
  и все admin-шаблоны — автономные HTML-файлы со встроенным CSS.
- JS — только vanilla, встроен в шаблоны.
- Все секреты — через `os.environ`, не хардкодить.
- Паттерн чтения переменных: `os.environ.get(key) or default` (не `get(key, default)`).
- CSRF: HTML-формы — hidden input, JSON fetch — заголовок `X-CSRFToken`.

## Что нельзя менять без подтверждения пользователя

1. **Схема БД** — любые изменения таблиц затрагивают существующих пользователей.
2. **`load_variant_tasks()`** — обеспечивает совместимость старых и новых вариантов.
3. **Маршруты** — изменение URL сломает существующие ссылки и закладки.
4. **Пароль сайта** — механизм закрытой регистрации.
5. **Форматы JSON контента** — variants, tasks, theory, uroki.
6. **Логика подсчёта баллов** — `secondary_score`, `score` в `user_results`.
7. **Права доступа** (`is_admin`) — механизм безопасности.
8. **CSRF-инфраструктура** — не добавлять `csrf.exempt` без аудита.
9. **`exam.html`** — автономный шаблон, специально не переведён на `base.html`;
   содержит встроенный CSS и JS для экзаменационного режима. Требует отдельного решения.
   (`reshenie.html` переведён на `base.html` в v1.11.0 — больше не в этом списке.)
10. **`start.html`** — автономная главная страница со своей дизайн-системой (v1.6.0–1.6.4);
    navbar встроен напрямую. Любые изменения — только отдельным согласованием.
11. **Admin-шаблоны** (12 файлов: `admin_panel`, `admin_task_form`, `admin_tasks_list`,
    `admin_tasks_view`, `admin_user_stats`, `admin_create_user`, `admin_practice_detail`,
    `constructor_gate`, `constructor_from_base`, `constructor_theory`, `constructor_uroki`,
    `constructor_editor`) — автономные, вне scope редизайна v1.6.5.
12. **`design-system.css`** — изменение токенов затронет все 16 пользовательских страниц одновременно.
13. **`base.html` и `components/`** — изменение затронет все 16 пользовательских страниц.

## Работа между несколькими ПК

### Принцип

Код и документация хранятся в git-репозитории на GitHub.
Секреты (`.env`) хранятся локально на каждом ПК — не синхронизируются.
Контекст для Claude Code восстанавливается через `CLAUDE.md`, `DEVELOPMENT_LOG.md`, `TODO.md`.

### Структура файлов контекста

| Файл | Назначение | Обновлять |
|---|---|---|
| `CLAUDE.md` | Статичное описание проекта и правила | При изменении архитектуры |
| `DEVELOPMENT_LOG.md` | История изменений, статус безопасности | После каждой рабочей сессии |
| `TODO.md` | Текущие задачи и известные проблемы | После каждой рабочей сессии |

### Порядок работы через GitHub

**Первичная настройка (один раз):**
```bash
git remote add origin https://github.com/<логин>/<репо>.git
git push -u origin main
```

**Начало работы на любом ПК:**
```bash
git pull origin main
# Убедиться, что .env существует и заполнен
# Если .env нет — скопировать из .env.example и заполнить
```

**Завершение работы на любом ПК:**
```bash
# 1. Обновить DEVELOPMENT_LOG.md и TODO.md (см. промпты ниже)
# 2. Закоммитить изменения
git add .
git commit -m "описание изменений"
git push origin main
```

### Регламент обновления документации

**После каждого крупного изменения кода:**
- Обновить соответствующий раздел в `DEVELOPMENT_LOG.md` (что изменено, почему)
- Закрыть выполненные пункты в `TODO.md`

**Перед переключением на другой компьютер:**
- Обновить `DEVELOPMENT_LOG.md` — текущее состояние, что сделано
- Обновить `TODO.md` — что осталось, что в процессе
- Сделать коммит и `git push`

**Перед коммитом:**
- Проверить, что `.env` не попал в `git add`
- Обновить `DEVELOPMENT_LOG.md` если были значимые изменения

**Перед новым релизом:**
- Добавить новую версию в `DEVELOPMENT_LOG.md` с полным списком изменений
- Обновить статус безопасности
- Закрыть все выполненные задачи в `TODO.md`
- Обновить версию в заголовке `DEVELOPMENT_LOG.md`

### Как восстановить контекст на новом компьютере

1. `git pull origin main`
2. Убедиться, что `.env` заполнен
3. Открыть Claude Code и использовать промпт начала сессии (ниже)
4. Claude прочитает `CLAUDE.md`, `DEVELOPMENT_LOG.md`, `TODO.md` и восстановит контекст

### Промпт начала новой сессии

Использовать после `git pull` на новом компьютере или после долгого перерыва:

```
Привет. Продолжаем работу над проектом EGEvolution.

Прочитай эти файлы по порядку и восстанови контекст:
1. CLAUDE.md — архитектура и правила проекта
2. DEVELOPMENT_LOG.md — что уже сделано и текущий статус
3. TODO.md — что нужно сделать

После прочтения:
- кратко подтверди текущее состояние проекта;
- напомни, что было сделано последним;
- укажи, какая задача следующая по приоритету из TODO.md.

Не вноси никаких изменений до моей команды.
```

### Промпт завершения рабочей сессии

Использовать перед `git commit` и переключением на другой ПК:

```
Рабочая сессия завершается. Обнови документацию.

Задача 1 — обнови DEVELOPMENT_LOG.md:
- добавь запись о сегодняшних изменениях (дата: сегодня);
- опиши что было сделано в этой сессии;
- обнови статус проверок если проводились;
- не удаляй историю предыдущих версий.

Задача 2 — обнови TODO.md:
- закрой [x] выполненные задачи;
- добавь новые задачи если они появились в ходе работы;
- обнови приоритеты если изменились.

После обновления файлов — покажи краткий список изменений,
чтобы я мог написать сообщение для git commit.

Код проекта не трогай.
```
